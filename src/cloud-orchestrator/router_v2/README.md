# router_v2 — the extended router in the backend (opt-in)

The same decision the evaluation measures, packaged for the backend: telemetry (+ optional operator note, + emergency-stop flag) -> one executed action.

- `rules.py`: **byte-identical copy** of `eval/spec/reference_labeler.py` (spec 1.0). A test compares the two files' hashes.
- `prompt.py`: the B-1.0 prompt and the strict reply parser, equivalent to `eval/baseline_b/prompt_b.py` (a test compares the prompt text and the parser on a corpus).
- `pipeline.py`: `decide(rec, note, call_model, estop)` — input check in code before any model call, exact numbers (no rounding, at most 2 decimals), one model call, strict parse, `rules.execute()`. `openai_model_call()` adapts an OpenAI-compatible client (one request, no retry, errors become faults).

**Switching it on.** A tenant in `scenario_registry.json` with `"router_mode": "extended"` (`Tenant-Alpha-Extended`) takes the whole `/api/simulate_agent` flow through `embodied_brain/extended.py`; tenants without `router_mode` run the old code path unchanged (tested). A request may carry `operator_note` (text) and `emergency_stop` (a JSON boolean; the only stop entry, text is never read as a stop).

**Order of the extended flow.** (1) `emergency_stop: true` answers with a stop at once, before the rate limit and with no external call at all; any other non-boolean value is an input error. (2) The raw request is checked with no defaults and no `int()` cast: a missing, null, non-numeric or out-of-domain value, a note over 500 characters, a bad `target_speed`, or a value with more than 2 decimals gives an explicit HALT result (HTTP 200, `input_valid: false`, `halt_reasons: ["INVALID_INPUT"]`), still with no external call. (3) Only then Cosmos (best effort) and the model, through a client with SDK retries off and a 60 s timeout, confirmed before the request (if it cannot be confirmed the vehicle halts). (4) The Router's whole decision is kept: `router_decision` in the response and, on a halt, the stop action itself carries `halt_reasons`, `holds` (COOL / LOCK), `deferred` (for example RETURN_TO_CHARGE) and `risk_set`. (5) Safety may only make the result stricter (BLOCK -> stop). (6) The Compiler is told the constraints, and its answer is **validated in code** before it leaves: only allowed actions, speed between 0 and the request's `target_speed`, at most 250 cm/s (2.5 m/s) while the decision has a speed cap, only `stop` while halted; anything else, including an unparseable or empty answer, becomes a stop with `constraint_violations` listed. An unexpected error is a stop with HTTP 500, never a silent pass. The IoT Hub path is not switched.

**What differs from the evaluation.** The extended flow uses the request's values as they are (no `int()` cast, no defaults); the physical gate is `rules.gate()` on those same values, so it is the evaluation's gate, not the legacy integer one. A live value with more than 2 decimals is rejected as out of contract, because the model could not see the exact number the code compares.

`tests/test_extended_endpoint.py` goes through the whole HTTP flow (Router, Safety, Compiler) with fake models and a fake Cosmos. `tests/test_router_v2.py` proves that, for every dev record and several reply variants (right, lax, prose, missing key, wrong status), this path and the evaluation path return identical executed actions.
