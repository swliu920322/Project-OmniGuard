# 指令文件的最佳实践（活文档，随使用迭代）

官方怎么说、加载机制是什么，见 [claude-code-memory-and-context.md](claude-code-memory-and-context.md)（稳定的事实）。**这份是我们自己的做法和度量，会变。** 每次改了 `CLAUDE.md`，或发现 AI 因为指令缺失或被忽略而出错，就在最后的迭代日志里加一行。

## 一、东西放哪

| 这条信息… | 放哪 | 例子 |
|---|---|---|
| 几乎每次对话都要用，读代码读不出来，不告诉就会做错，相对稳定 | 根目录 `CLAUDE.md` | 命令、冻结文件、不许调模型、检查失败时停下 |
| 只在某个目录里工作时才需要 | 那个目录的 `CLAUDE.md`（碰到该目录的文件才读） | 只和 `eval/` 有关的措辞规则（现在不拆，见第四节） |
| 多步骤、很少用、一次要好几步 | skill（描述常驻，正文触发才读） | "做一次真实模型运行"：授权、上限、健康检查、封存、回执 |
| 会变的事实：结果、数字、状态、进展 | 文档加测试，**不放** `CLAUDE.md` | `RESULTS.md`，`tests/test_round2_numbers.py` |
| 代码怎么走 | 代码本身和 `docs/guide/` | 请求路径 |
| 怎么走到这一步的 | 提交说明和 git 历史，不新建文件 | 设计取舍 |
| 跨项目的个人偏好 | 用户层记忆 | "改动前先给审计卡" |

## 二、怎么写一条规则

1. 写成 **"当 X 时：做 Y。由什么检查"**。没有自动检查就写 `No automatic check`，不要假装有。
2. 一条规则只说一件事；用真实的路径和命令，不写"相关文件"。
3. 不写读代码就能得到的叙述（会过时，官方也明确列为不该写的）。
4. 同一条规则被 AI 反复忽略时，**不要加粗、不要重复**，把它变成测试或钩子。这是文章里"关键规则写两遍，一遍说明，一遍机械检查"的意思。
5. 给人看的维护说明放 `<!-- ... -->`，官方说它在注入前被去掉，不占 token。

## 三、仓库里已有的机械防护（`tests/test_claude_md.py`）

| 检查 | 防什么 |
|---|---|
| 大小绊线 7 KB、60 行 | 慢慢变长。这是有意选的数字，不是官方要求（官方建议 200 行） |
| 提到的 `make` 目标、路径都存在 | 文档指向不存在的东西 |
| 每条规则都写 `Checked by` 或 `No automatic check` | 把没有保护的规则写成好像有保护 |
| 说"冻结"的文件确实在冻结清单里 | 说法和清单不一致 |
| 自检：给一份有错的假文本，检查必须报错 | 检查本身是空的 |

## 四、现在最值得做的优化（按收益排序）

数据来自 2026-11-21 的 `/context`：`CLAUDE.md` 约 3k tokens（0.3%），skill 描述 5.9k（0.6%），对话消息 875k（87.5%），其中命令输出 180k（18%）。

| # | 做什么 | 预计收益 | 成本和风险 |
|---|---|---|---|
| 1 | **限制命令输出**：用 `head`、`tail`、`grep`，大文件用带范围的读取，不要整份打印 | **最大**：这个会话里命令输出占 18%，约 90k 可省 | 是 AI 的行为，不是文件。可以在 `CLAUDE.md` 加一行规则（`No automatic check`），要你点头 |
| 2 | **一个任务一个会话**，快满时主动 `/compact`，不等自动压缩 | 大：这个会话到 91% 才处理；压缩会丢早期细节 | 无 |
| 3 | 关掉不用的 skill：先 `/skills` 看，再按官方提到的 `/skill-doctor` 找该关的 | 小：最多约 5k tokens，约 0.5% | 53% 来自 claude.ai 同步，关的位置在账号侧；我没核实具体步骤 |
| 4 | "做一次真实模型运行"做成 skill | 中：这套流程我们摸索过一次，下次可以直接用；新增约 100 tokens 的常驻描述 | 要写一份约 60 行的流程，等真有下一次再做 |
| 5 | 子目录 `CLAUDE.md`（`eval/` 的措辞规则） | 小：现在 45 行远低于 200 行 | 多一个指令文件；规则长到约 100 行再做 |

不要做：用 `@path` 导入来拆文件（官方：不省上下文）；为了凑上限往里填内容。

## 五、怎么衡量

- 改完 `CLAUDE.md` **开新会话**（官方：会话中途改不生效），跑 `/context all`，记下 Memory files 一栏。
- 要看 skill 的常驻成本：`/doctor`、`/skill-doctor`。
- 要看哪些指令文件何时被加载：官方的 `InstructionsLoaded` 钩子。
- 同一个任务用不同写法各跑一次，比较 AI 是否出错；没有这个对比，"更短更好"只是猜测。

## 八、skill：总结（留给之后思考和迭代）

### 1. 它和 `CLAUDE.md` 的区别

| | `CLAUDE.md` | skill |
|---|---|---|
| 什么时候进上下文 | 每次会话整份读入 | **描述常驻**，正文触发时才读 |
| 写法 | 说明和规则 | "当 X 时做 Y"，触发条件写在描述里 |
| 常驻成本 | 全部内容 | 只有描述（本会话 31 个共 5.9k tokens） |
| 适合放 | 每次都用得上的 | 多步骤、很少用的流程 |

### 2. 值不值得写：三个条件同时成立

1. 一套**多步骤**的流程会**反复出现**；
2. 每次都要**做对**，漏一步就出事；
3. 做没做对**能被检查**。

| 本项目的流程 | 会反复出现吗 | 现在有保护吗 | 结论（2026-11-22） |
|---|---|---|---|
| 做一次真实模型运行 | 很少，额度只剩 3 次请求 | 运行器会拒绝越权，有测试 | 下次真要跑再写 |
| 更新证据文档（局限、索引、数字） | 偶尔 | 孤儿文档、数字一致、链接三个测试 | 不需要，测试比 skill 强 |
| 提交和推送前检查 | 每次 | 手写正则扫描 | 先试内置的 `security-review`，不新建 |
| 冷读测试 | 偶尔 | 提示词文件和评分表 | 不需要 |

**现在项目自己的 skill 是 0 个，这是有意的。**

### 3. 写好一个 skill 的 8 问（来自 `refer/get.md` 第一篇）

触发条件具体吗？输入输出明确吗？先做什么后做什么？有失败处理吗？有禁止事项吗？有验证命令吗？记录已知坑了吗？能被测试打脸吗？**过不了 5 条基本可删。** 另外：描述要短（官方：描述加触发说明在列表里最多 1536 字符）；写明"不用于什么"。

### 4. 有没有现成的标准 skill

| 来源 | 说明 | 做法 |
|---|---|---|
| **内置，已装好** | `code-review`、`security-review`、`simplify`、`run` 等 | 先用这些，不多装；用了要写明"用了" |
| **开放生态**（`find-skills` 用 `npx skills find` 搜、`npx skills add` 装，入口 skills.sh，以上来自它的说明文件，站点本身没核实） | 别人写的，质量参差 | 只搜索；评估后再装 |
| **自己写** | `skill-creator` 能写并测试 | 等真有需要的流程 |

装第三方 skill 之前：读完 `SKILL.md` 当代码审；用 8 问打分；想清楚它的描述每一轮都占上下文；确认它写的是**这个项目**的事。

### 5. 本项目的一次教训：`arch-audit`（2026-06-28 提交，2026-11-22 删除）

按 8 问约 1/8，属于文章点名的"玄学咒语"。五个气味，以后看到就警惕：

1. **人设和口号**（"架构之神""暴力结论"）代替操作步骤；
2. **规则属于别的系统**（Redis 状态机、向量检索 17 ms），而本项目没有这些；
3. **触发太宽**（"重构、审查、优化"几乎任何请求都沾边）；
4. **没有输出格式**，无法判断它做没做对；
5. **没有验证**，也没有任何测试能反驳它。

它的代价不在那约 20 个 token，而在它被触发时会把不属于本项目的规则当成红线塞给 AI。

### 6. 常驻成本的构成（2026-11-21 的 `/context`）

31 个 skill 共约 5.9k tokens：claude.ai 同步 13 个约 3.2k（53%），内置 16 个约 2.6k（44%），用户目录 1 个、项目 1 个共约 130（2%）。每新增一个 skill，常驻描述加约 20 到 480 tokens。**这不是主要成本**（总上下文的 0.6%），但它是"你没选择、也没用"的成本，值得用 `/skill-doctor` 清一次。

### 7. 一个好 skill 的骨架（示例，没有创建）

```
---
name: run-real-evaluation
description: 当用户明确授权对模型发起真实评测请求时使用。不用于离线复算、写文档或改代码。
---
1. 先确认所有者给出了次数、token、美元三个上限；没有就停，去问。
2. 运行 plan，看预计请求数和已用额度；超过剩余额度就停。
3. 先做 2 条的健康检查；不通过不进入完整运行。
4. 完整运行用 --after-health latest；不重试，不中途改文件。
5. 结束后读 REPORT.md，把结果和局限写进 LIMITATIONS，提交。
禁止：打印或提交密钥；放宽预算；用重试掩盖失败。
验证：tests/test_safety_compiler_run.py；运行目录的 SHA256SUMS 能校验。
已知坑：提供商不遵守 max_completion_tokens（预算按 2048 预留）。
```

### 8. 用这一节思考时可以问自己

- 这个流程**这个月**出现了几次？不到三次就别写 skill。
- 一个不知道项目背景的 AI 读到描述，**能判断该不该触发吗**？
- 它出错时，是**测试**先发现，还是靠人看？没有测试就不要假装可靠。
- 我是真的**用了**某个 skill，还是只是**知道它存在**？（见迭代日志 2026-11-22。）
