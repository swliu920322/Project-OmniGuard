# 职业路线：把前端、AI应用、业务harness与Azure连起来

更新：2026-11-10。用途是帮助选择岗位、安排学习和组织实践证据，**不是招聘结果预测，也不是已经拥有某种职级的证明**。本文依据本人已讲述的兴趣、现有项目和少量公开岗位／官方资料作判断，没有完整核验履历、认证状态或目标地区的招聘市场。

这是一份职业方向专题，不替代[面试主手册](INTERVIEW_DEEP_DRILL_zh.md)和[日常学习练习](RECOMMEND_LEARNING_zh.md)。后续更新本文件，不再另建职业review或多个路线版本。本次只写文档，不启动新项目、云部署、模型调用或付费考试。

## 一、先给建议：AI应用为主线，云为交付环境，前端为已有优势

建议先探索：

> **云上AI应用／AI全栈开发 → 能独立交付业务智能体 → 有实际交付与运行经验后，再评估应用架构或解决方案方向。**

箭头表示可以积累的能力，不表示必须跳槽三次、保证晋升或每个人都适合做架构师。若更喜欢编码，可以持续深入应用工程；若更喜欢平台与排障，也可以转向AI平台／DevOps，而不必以架构师为终点。

这条建议基于你目前讲过的三件事：

- 有前端实践和长期形成的组件组织习惯，希望把前端当作辅助交付能力。
- 对云服务、SDK与业务组合有兴趣，并自述取得了多项Azure认证。
- 已通过OmniGuard接触模型接入、程序约束、评测和证据，但仍在补足代码理解与独立解释能力。

目前不建议把所有经验清零，重新包装成纯算法新人；也不建议仅凭证书把自己定位为生产云架构专家。**要做的是让已有经验参与新的交付，再明确哪些环节真正由自己掌握。**

### 还不知道的条件，怎样影响选择？

| 尚待本人补充 | 为什么影响判断 |
|---|---|
| 原有工作年限、职位、代表性成果 | 决定如何利用资历，不能仅按AI经验长短判断总职级 |
| Python／SQL／服务端能独立做到哪里 | 决定先投AI全栈还是偏后端的应用工程 |
| 目标城市、国家、语言与工作许可 | 决定实际岗位、Azure生态和招聘条件，不能由项目推断 |
| 编码、需求沟通、部署排障各自兴趣 | 决定应用研发、方案实施与平台路线 |
| 可投入时间、是否急需入职 | 决定先投递并补短板，还是容许较长实践 |

这些不是要求现在全答完才能行动。先用已有材料分析3～5份目标JD，再补最影响选择的信息。

## 二、先分清技术：它们不是互相排斥的赛道

贯穿例子：一名员工说：“设备报E17，帮我查处理办法，必要时建报修单。”

这是**未来可以选择的教学项目**，不是OmniGuard当前已有功能，也不是来自真实企业的需求。

| 层次 | 回答的问题 | 在例子中的作用 |
|---|---|---|
| 前端／产品交互 | 用户怎样发起、看懂和控制任务？ | 展示引用、查询进度、确认报修内容 |
| RAG（检索增强生成） | 回答需要的知识在哪里？ | 从对应型号手册中找到E17说明 |
| 工作流编排 | 哪些步骤必须按顺序执行？ | 确定设备→查询→准备工单→确认→创建 |
| Agent | 哪些下一步允许由模型按结果选择？ | 信息不足时追问，或在受限工具中选择下一项查询 |
| 业务harness | 整个执行怎样被约束、记录和恢复？ | 管理权限、状态、工具、预算、停止条件和结果确认 |
| 云平台 | 计算、存储、检索和运维由什么承载？ | 身份、API、数据库、部署、日志与告警 |
| 评测 | 怎样知道比原来好、哪里仍会错？ | 分别检查检索、回答、工具参数与最终任务状态 |

不要把“上层”理解成更高级或更值钱。检索差、权限错、任务状态丢失，任何一层都可能让应用失败。

## 三、RAG要学到什么程度，才对面试有帮助？

RAG不只是“把PDF放进向量库”。至少要能解释下面这条链路：

> 资料来源与版本 → 文档解析 → 分块 → 建索引 → 检索 → 必要的重排 → 组装上下文 → 带来源回答。

微软的RAG指南也将数据准备、分块、嵌入、索引、检索与评测分别讨论。框架和托管服务可以减少实现工作，但仍需验证每一阶段是否满足任务要求。[微软RAG设计与评测指南](https://learn.microsoft.com/en-us/azure/architecture/ai-ml/guide/rag/rag-solution-design-and-evaluation-guide)

### 用E17例子理解真正的工程问题

| 现象 | 先检查什么 | 可以怎样验证 |
|---|---|---|
| 回答用了另一型号手册 | 型号过滤、元数据、检索结果 | 用同故障码但不同型号的问题检查 |
| 文本相关却缺关键处理步骤 | 分块边界、相邻段落和表格解析 | 查看原文，核对返回片段是否完整 |
| 引用是对的，答案却添了原文没有的结论 | 生成约束与答案依据 | 逐项检查回答主张是否有资料支持 |
| 手册已更新但回答仍旧 | 索引更新、版本选择、缓存 | 替换资料版本，检查旧内容是否仍被使用 |
| 无资料也给确定答案 | 拒答与转人工条件 | 使用资料未覆盖的问题 |
| 用户看见无权访问的资料 | 身份与服务端检索权限 | 用不同授权用户测试，不能靠提示词隐藏 |

### 建议先做的比较

选少量代表问题，比较“简单关键词检索”与一种语义／混合检索方案。先确认业务需要，再决定是否增加重排和查询改写。不要为了展示技术，把所有组件同时堆进来，导致无法解释哪一项起作用。

检索是否找对与最终回答是否正确应分开报告。指标可以包括相关资料的Recall@k、引用是否支持答案、拒答是否合适、延迟与成本；选择哪些由具体任务决定，不要求一开始实现所有指标。

**掌握检查：** 能追查一个错误答案究竟错在资料、检索还是生成，而不是每次都改提示词。

## 四、Agent编排要学什么，不必先做多个Agent

“编排”是安排工作，不必每一步都由模型决定。固定程序通常更容易检查；只有无法提前写死的决策，才考虑交给模型。

Anthropic区分了预定义代码路径的workflow与模型动态控制流程的agent，并建议从简单方案起步。这是一个有用的设计区分，不是要求采用其产品或把所有业务都变成自主Agent。[Building effective agents](https://www.anthropic.com/research/building-effective-agents)

### 建议按这个顺序理解

1. **普通业务API**：先不用模型，能够查设备、准备工单、创建工单。
2. **固定工作流**：程序决定顺序，步骤有明确输入、结果和失败出口。
3. **工具调用**：模型只能从允许的工具中选择，服务端验证参数与权限。
4. **有限动态决策**：例如缺设备型号时追问，遇到无资料时停止，不允许无限循环。
5. **确有需要才拆角色或多Agent**：说明拆分带来的效果，核对新增延迟和成本。

**工具调用不是把模型给的文字当代码执行。** 例如模型提出调用 `create_ticket`，后端仍需检查设备ID、权限、用户确认、重复执行与业务结果；不把任意SQL或任意网络请求当作默认工具。

### 面试里要能回答的六个问题

- 为什么这一步需要模型，普通条件判断是否够用？
- 模型选错工具或缺参数时，谁来拒绝？
- 任务完成由哪个业务状态证明？
- 模型反复调用同一工具，怎样停止？
- 用户取消时，已经完成的操作怎样处理？
- 程序重启后，能不能知道上一轮做到哪里？

这些问题比会列出多个框架名称，更能检验是否理解任务执行。

## 五、业务harness到底是什么技术？

本文用“业务harness”表示围绕模型建立的业务运行与控制环境。这个名称没有一个对所有公司都相同的组件清单；招聘中也可能称Agent平台、业务编排、智能体工程或AI应用基础设施。

可以从一个小型运行记录理解，而不是先设计通用平台：

```text
用户与授权范围
  ↓
任务输入、任务ID、状态
  ↓
准备上下文／检索资料
  ↓
模型或代码选择下一步
  ↓
工具白名单＋参数校验＋权限＋必要确认
  ↓
执行结果记录
  ↓
继续／等待确认／完成／失败／结果待确认
```

### 技术能力与业务意义

| 能力 | 需要的技术 | 解决什么 |
|---|---|---|
| 输入与输出契约 | 类型、JSON Schema或等价校验 | 拒绝缺字段、错单位和不合法参数 |
| 工具适配 | HTTP/API、SDK、错误映射 | 连接已有业务系统，而不把它们全部重写 |
| 状态管理 | SQL、事务、状态机 | 知道当前步骤、已做动作和恢复位置 |
| 权限管理 | 身份、资源授权、服务端检查 | 不让模型扩大用户权限 |
| 重复执行控制 | 业务幂等标识、唯一约束、去重 | 降低重复创建或重复提交的风险 |
| 长任务管理 | 异步任务、队列或工作流持久化 | 请求断开后仍能追查任务，按需要恢复 |
| 运行限制 | 截止时间、调用／费用限制、取消 | 防止无限运行或不可控消耗 |
| 人工确认 | 确认记录与可执行动作绑定 | 用户确认的是这一次、这些参数的操作 |
| 可观测与评测 | 日志、trace、测试数据和评分 | 定位哪一步错、修改有没有帮助 |

MCP可以是工具接入协议，框架可以帮助编排；它们不自动实现表中全部业务责任。普通函数工具也能开始练习，不需要先自研协议或平台。

**你当前的连接点：** OmniGuard已有契约、受限输出、风险合成和评测，但不是完整的企业harness。下一步适合补“有状态的业务任务”，而不是把现有函数重新命名后宣称平台已经完成。

## 六、SDK为什么能减少代码，却不能免去工程判断？

你的想法——使用SDK和托管服务减少重复劳动、聚焦业务——是合理的。面试不应以手写了多少基础设施代码判断价值。

但应用需要理解服务接口的语义：

| SDK能帮助做的事 | 应用仍需决定的事 |
|---|---|
| 发送工单创建请求 | 超时后是否已经创建，能否重试 |
| 返回模型工具调用 | 该用户是否有权执行，参数是否有效 |
| 返回搜索结果 | 资料是否适用、版本是否正确 |
| 抛出网络异常 | 如何保留状态、向用户说明和继续确认 |
| 提供默认重试 | 业务是否幂等、是否超出任务期限 |
| 记录基础请求信息 | 怎样把用户任务、检索、模型和工具步骤串起来 |

### 必须理解的例子：超时不等于没有执行

1. 服务端已经创建工单，但响应在网络中丢失。
2. 客户端收到超时，不知道是否成功。
3. 若简单重发，可能创建重复工单。
4. 可以考虑由业务系统支持幂等标识，或按关联ID查询确认；不能假设所有第三方服务都有相同支持。
5. 在结果确认前，向用户展示“创建结果待确认”，不让模型编造一个成功工单号。

这不是要求实现完美的“全链路恰好一次”，而是承认结果可能未知，并设计可检查的处理。

面试可以这样回答：

> 我优先用成熟SDK与托管服务，但会核对超时、重试、错误和返回值语义。业务层仍负责权限、状态、重复执行和最终结果确认。选择SDK减少的是重复实现，不是业务责任。

## 七、云方向怎样和AI路线结合？

云不是只有集群运维一种工作。可以通过不同责任范围进入：

| 方向 | 日常工作重心 | 当前可迁移的基础 | 还需要的证据 |
|---|---|---|---|
| 云上AI应用开发 | API、数据、模型与业务集成 | 前端、云知识、现有模型评测 | 独立后端编码、一次部署与故障定位 |
| AI全栈开发 | 用户交互到后端任务交付 | 前端经验、仿真界面和后端流程 | 完整业务任务、状态展示与确认 |
| AI方案实施／交付 | 需求澄清、原型、集成、验收 | 认证知识、沟通与项目理解 | 需求取舍、运行记录、交付说明 |
| AI评测工具／平台开发 | 数据、评分、运行器和结果分析 | 当前冻结与评测流程 | 更独立的编码、统计与任务评测 |
| DevOps／平台工程 | 流水线、配置、部署、监控与恢复 | Azure及DevOps知识 | 可操作的CI/CD、回滚与排障实践 |
| 云支持／技术支持工程 | 定位用户系统与服务问题 | 云知识、解释问题的兴趣 | 日志与网络诊断、沟通、工单与根因记录 |
| 解决方案架构 | 需求与约束转成整体设计 | 广泛云知识、架构兴趣 | 真实取舍、交付及运行反馈，不只是画图 |

以上是方向分析，不表示所有公司如此分工。实施与支持可能涉及客户沟通、现场或值班，平台岗位也可能有较强运维要求，需逐份JD核对。应用开发同样有运行责任，不应当成“没有风险的云岗位”。

微软的Azure AI Cloud Developer角色说明把开发、部署、安全、监控和排障放在同一个生命周期内，可用来理解“云上AI应用”如何组合能力；不是建议你现在再考这张证书。[官方角色说明](https://learn.microsoft.com/en-us/credentials/certifications/azure-ai-cloud-developer-associate)

## 八、认证怎样转成面试证据？

你自述已取得解决方案架构、AI与DevOps相关Azure认证。具体正式名称、取得时间、有效状态和考核范围需要本人核对；本文不把某个口头名称自动对应到一个当前认证。

认证能说明系统学习背景，不能单独证明值班、客户交付或事故处置经历。不要为了淡化这点隐藏认证，也不要用Expert等级替代工作职级。

| 学过的主题 | 适合补的实践证据 | 面试可追问 |
|---|---|---|
| 身份与权限 | 一个资源授权测试，记录允许／拒绝情况 | 为什么用户A不能读B的资料？ |
| 计算与部署 | 一个可部署、可停止、可清理的应用 | 版本错了怎样回滚？ |
| 数据与存储 | 明确任务表和状态转换 | 重启后如何避免重复操作？ |
| 网络与配置 | 一次故障的定位记录 | 是地址、DNS、身份还是服务故障？ |
| 监控 | 一条任务贯穿多个阶段的追踪 | 哪段慢，依据是什么？ |
| DevOps | 一次测试失败阻断或回滚的演练 | 失败后有什么证据、怎样恢复？ |
| 成本 | 费用估算和实际用量记录 | 价格假设、未知用量和上限怎样处理？ |

微软对Azure架构师的描述强调业务需求与整体设计；DevOps角色也覆盖交付、监控与反馈。可以借这些定义检查能力，而不是只整理服务名。[架构师角色](https://learn.microsoft.com/en-us/credentials/certifications/azure-solutions-architect/)、[DevOps角色](https://learn.microsoft.com/en-us/credentials/certifications/devops-engineer/)

## 九、岗位选择：看责任，而不只搜技术词

建议先看AI应用／AI全栈／云上应用开发，兼看评测工具和方案实施。偏算法训练、机器人导航控制或大型生产集群SRE，目前项目证据距离更远；若有其他相关经历，应另外计入，不由本文否定。

### 公开岗位能说明什么？

检索时，小鹏的Agent工程岗位列出工具编排、失败恢复、RAG、评测和可观测，并要求相应开发经历；波克的岗位也提到工具调用、上下文、RAG与Harness。这些样本支持“能力组合有岗位对应”，不证明当前岗位全部开放、市场占比或你已经符合其资历要求。[小鹏招聘](https://xiaopeng.jobs.feishu.cn/index/position/7697084808392083731/detail)、[波克招聘](https://boke.jobs.feishu.cn/index/position/7698219095988930854/detail)

### 给每份JD做一张对应表

| 要求 | 是核心责任还是加分项？ | 我的实际证据 | 差距／下一步 |
|---|---|---|---|
| Python服务开发 | 待按JD判断 | 能解释的函数、独立修改、测试 | 不只写“用过FastAPI” |
| RAG | 待按JD判断 | 当前OmniGuard没有 | 需要新的检索实践，不改称已有能力 |
| 工具与任务编排 | 待按JD判断 | 当前有固定模型流程 | 业务工具与有状态执行待补 |
| 评测 | 待按JD判断 | 冻结、评分与规则对照 | 区分本人实施与AI协助 |
| 云部署与运行 | 待按JD判断 | Bicep、历史说明、认证 | 当前可运行与恢复证据不足处明说 |

先排除地点、工作许可、必须学历／年限等硬条件冲突，再比较核心责任。不要仅按“满足多少关键词”决定匹配度，也不要因为列了十个加分框架就先学十个。

## 十、一个可选的贯穿实践：资料查询到报修任务

目的不是再做一个大平台，而是补上当前缺少的两段：**从知识找到依据，从建议完成业务动作。**

### 范围先定小

- 用户：模拟员工与处理人员，使用测试身份。
- 资料：少量公开或自写的设备说明，明确是教学资料，不是真实安全操作指导。
- 工具：查询设备信息、准备报修内容、创建模拟工单、查工单状态。
- 输出：有引用的资料回答，或可查证的工单ID／待确认状态。
- 排除：真实生产写入、付款、控制实体设备、通用浏览器操作、多Agent平台。

### 分四个增量做，不一次全接

| 增量 | 新增什么 | 看见什么才算完成 |
|---|---|---|
| A：不接模型的业务骨架 | API、任务表、状态、假业务服务 | 能创建／查询任务，权限和重复提交有测试 |
| B：最小RAG | 文档检索、来源与拒答 | 能区分错资料、错检索、错生成 |
| C：受限工具调用 | 模型提议、代码校验、确认后执行 | 模型说完成之前，已有真实模拟业务结果 |
| D：云交付与观测 | 容器／托管运行、配置、追踪与清理 | 部署记录、一次故障定位、恢复与费用记录 |

先固定一个简单工作流；只有固定顺序确实不能满足任务时才增加Agent动态选择。不为展示而加入队列、复杂缓存或多Agent；先说明当前瓶颈是什么。

以上是建议，不是本次已授权实施。云资源、模型调用、真实业务接口和费用，要在具体计划、范围和上限明确后再决定。

## 十一、怎样量化，让简历不再只剩满分？

新实践优先选择能说明业务链路的指标，先固定定义再运行：

| 问题 | 可记录的指标 | 注意分母与边界 |
|---|---|---|
| 是否找到正确依据？ | Recall@k／证据命中数 | 需要定义相关资料，检索命中不等于答案对 |
| 回答是否受依据支持？ | 支持性、引用与拒答检查 | AI评分应抽查，不自动当专家真值 |
| 任务是否完成？ | 实际业务状态确认的完成数／任务数 | “模型说完成”不计完成 |
| 工具是否调用正确？ | 工具、参数和授权检查 | 错工具与接口失败分别统计 |
| 是否重复执行？ | 注入故障场景下重复业务记录数 | 零次仅限这些场景，不证明永久不会重复 |
| 等待代价多大？ | 端到端与阶段耗时，中位数、P95、失败 | 起止点一致，失败与未知用量不隐藏 |
| 修改有没有帮助？ | 同题同政策下的方案差异 | 区分开发与独立测试，不挑一跑 |
| 用户体验如何？ | 完成步骤、等待、人工修正 | 没有真实用户就不能宣称用户效率提升 |

示例：比较固定工作流与允许模型选择工具的方案，检查任务完成、错误工具调用和时间成本。固定流程更好也是有效结果；无需设定AI方案必须胜出。

不要事先承诺“效率提高50%”。若要写节省时间，需明确原流程、操作者、任务、起止点和样本；仅测一次演示不能代替业务收益。

## 十二、学习顺序：先补能独立操作的基础

| 顺序 | 学什么 | 一项可检查的输出 |
|---|---|---|
| 1 | Python／TypeScript服务、HTTP、JSON、SQL | 独立改一个API，解释查询与测试 |
| 2 | 状态机、事务、幂等与失败语义 | 解释一次“请求超时但业务可能成功” |
| 3 | RAG基本链路与分层评测 | 定位一个错误答案并给出验证记录 |
| 4 | 工具调用与有限工作流 | 用户确认后才执行，结果可查 |
| 5 | 容器、身份、部署、监控 | 一次部署与一次故障恢复记录 |
| 6 | 框架、MCP或更复杂Agent | 解释它解决哪项已遇到的问题 |

顺序可随已有能力调整，不是要求学完基础才能投简历。框架可以早用，但应能画出它隐藏的调用、状态和错误处理，不能只会复制教程。

每轮只补最影响目标岗位的一项。暂不把训练大模型、全面微调、完整机器人导航、Kubernetes集群或自研Agent框架一起列为必修。

## 十三、面试怎样应对“出了问题怎么办”？

不是背故障百科，而是展示有依据的排查与恢复顺序：

> 观察事实 → 判断范围 → 控制影响 → 分层定位 → 恢复 → 验证与复盘。

例如：“用户说创建工单卡住了。”

1. 找任务ID与时间，确认是等待模型、等待确认、调用业务系统，还是响应未返回。
2. 在结果未知时避免继续触发重复创建，检查已有业务记录。
3. 根据日志与追踪区分接口错误、权限、参数、排队或服务依赖；不先断言网络慢。
4. 按既定策略查询确认、重试可重试步骤，或转人工；不对所有步骤一律重试。
5. 检查最终工单是否存在、是否重复，前端展示是否与业务状态一致。
6. 留下一条可复现用例，说明哪里需要改，测试怎样防止再次出现。

如果缺少追踪，正确回答是“现有记录无法定位，我会先补哪项观测”，而不是编出根因。个人演练写“本地／测试环境演练”，不要写成处理过线上事故。

### “面试不关心做了什么”需要修正

交付成果、理解深度和变化条件下的判断，三者都重要。成果是追问的起点；排障是检查理解的一种方式。不要因此忽视成果，也不要把自己没处理过的生产事故补进经历。

## 十四、如何整理简历与作品集？

### 当前OmniGuard的位置

它适合支撑模型接入、约束、评测与证据管理，不能支撑已有RAG、真实机器人闭环或企业任务自动完成的声明。固定合成记录两跑300/300、55例压力分项等数字，以[正式报告](../../eval/report.md)为准；本人贡献单独确认。

### 如果以后完成新的贯穿实践

它补充知识检索、业务工具、任务状态和云运行；与OmniGuard各有用途，不把两份项目数字相加制造规模。先保留原始记录，再根据实际结果写简历，本文不给尚未发生的成果填数字。

### 定位表达可以这样起步

> 有前端工程实践和Azure相关学习背景，向云上AI应用开发方向发展，重点学习模型接入、业务流程、输出约束与效果评测。

这是方向表述。只有掌握并实际交付后，才把“学习”改为“负责／完成”。有已有工作成果时优先用成果，不把个人简介写成技术愿望清单。

针对不同岗位调重点：

- AI应用：业务任务、模型接口、工具与验证。
- AI全栈：用户控制、交互状态、后端执行与模型结果贯通。
- 评测开发：数据、评分、失败归因和可复核结果。
- 云实施：部署、身份、配置、成本、观测与恢复。

## 十五、接下来怎么行动，不继续无限扩材料？

1. **收集3～5份真实目标JD。** 选两个相近方向，记录硬条件、核心交付与加分项。
2. **盘点已有证据。** 前端实际成果、Azure认证准确名称与状态、OmniGuard中能独立解释的代码和贡献。
3. **选一个最大缺口。** 是服务端编码、RAG、工具执行，还是部署排障？不要同时开四条学习线。
4. **做一项小验证。** 形成输入、行为、结果、限制和可运行检查；需要费用时先明确预算。
5. **开始有针对性的投递与模拟面试。** 用反馈调整差距，不以“全部学完”为投递前提，也不保证反馈都反映真实能力。
