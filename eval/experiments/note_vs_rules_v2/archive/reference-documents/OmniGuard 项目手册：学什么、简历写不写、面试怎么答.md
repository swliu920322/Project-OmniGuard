# OmniGuard 项目手册：学什么、简历写不写、面试怎么答

Nov 3, 2026 · @Mason LIu

一句话结论：简历要写，但写得克制，只用论文里能对上的数字；学习只做 7 件事，约 16 小时；面试准备 9 个常见追问。每一节开头都有“这一节讲什么”，表格里有“白话”列，不懂技术也能跟上。

## 先认识几个词

这一节讲什么：后面反复出现的词，先各用一句大白话说清。

| 词 | 白话 |
| --- | --- |
| 模拟 AGV | AGV 就是仓库里自己跑的搬运小车。项目里没有真车，是用程序假装小车在发数据。 |
| 云端 / 边缘 | 云端是远处的大服务器，聪明但有网络延迟；边缘是小车旁边的小电脑，笨一点但反应快。 |
| 智能体（Agent） | 一次专门负责某件事的大模型调用。这个项目有三个：Router（分流）、Safety（判断是否危险）、Compiler（把决定写成具体指令）。 |
| benchmark（基准测试） | 一套固定的考题，用来给系统打分。 |
| 标签 | 考题的标准答案，比如“这个场景算危险”。标准答案本身错了，分数就没有意义。 |
| 随机种子 | 让“随机出题”可以重现的编号。种子相同题目就一样；种子不同的两次成绩，不能直接比。 |
| 混淆矩阵 | 一张“标准答案 对 系统答案”的对照表。对角线是答对的，其余是答错的。 |
| 召回率 | 真正危险的情况里，系统抓住了多少。安全系统宁可误报，也不能漏报，所以最看这个。 |
| 提前退出 | 前一步已经能下结论（比如明显危险就直接停车），后面的模型就不再调用，省时间。 |
| 门控 | 写死在代码里的硬规则，不经过大模型。例如“传感器坏了就一律停车”。 |
| 延迟 | 从发出消息到拿到结果花的时间。 |
| 反事实估算 | “如果当时没这么做，会多花多少时间”的推算，不是实际测出来的，不能当成实测数字。 |

## 一分钟看懂这个项目

这一节讲什么：让一个不懂技术的人也能复述这个项目。

小车每秒把位置、速度、前方距离发到云端。云端让三个大模型接力判断：第一个看是不是需要关心的情况，第二个判断危不危险，第三个把决定写成指令发回小车。问题是这一整圈平均要约 6 秒，而小车一秒能走 2.5 米，所以真正的紧急刹车不能等云端，必须在小车本地完成；云端负责理解情况、留下可以事后审查的记录。

你做的事：搭起这条链路（在 Azure 上真实部署过），再用 200 个模拟场景给它打分，并且回头检查打分方法本身有没有问题。

## 论文里该学什么

这一节讲什么：论文里有 7 块内容值得学到“被追问也能答”的程度，其余不用碰。不再给项目加功能，只把已有的设计、失败和证据学扎实。工时是我的估计，共约 16 小时，前 3 项可以和行动计划的第 2 周合并做。

| # | 要学的 | 白话说明 | 学到什么程度算够 | 工时 |
| --- | --- | --- | --- | --- |
| 1 | 延迟变距离，以及这个算法缺什么 | 反应慢多少秒，车就多冲出去多少米，即 距离 = 速度 × 时间。论文算出临界速度 v\_crit = 1.2 m ÷ 5.68 s ≈ 0.21 m/s，也就是超过这个速度，云端回复到达前车就已冲过刹车距离。论文第 5.7 节自己承认这是简化，因为实际刹车距离随速度的平方增长。 | 能自己推出 d = v × T；能说出它忽略了传感器延迟、执行器响应和路面。 | 2.5 h |
| 2 | 评测的四个层次和标签的定义 | 同一道题有四个“答案”：标准答案（标签）、Router 的判断、Safety 的判断、最终动作。论文里 Router 对 172 个有标签样本答对 162 个（94.19%），但这个“对”是对着标签的，标签如果有问题，94% 就没有意义。 | 能不查资料讲清为什么 94% 可能没意义；能读混淆矩阵，会算召回率。 | 3 h |
| 3 | 基线对照，以及“不同种子不能直接比” | 基线就是“最笨的对照组”，这里是只用一句话提示的单个模型。它在关键障碍上抓到 44/44，而三智能体是 86.8%。但两次测试抽到的场景不一样（44 个对 38 个危险场景），指标口径也不同，所以不能说谁更准。 | 能说清这两个数为什么不能直接比，以及怎样设计一次公平的对照。 | 1.5 h |
| 4 | 用代码硬规则，而不是靠提示词约束模型 | 论文的教训 1：在提示词里写“传感器异常就不要生成命令”，模型反复不听；后来改成放在中间件里的代码规则（门控），才可靠。 | 能写出约 15 行伪代码，并说清哪些规则必须写进代码。 | 1.5 h |
| 5 | 事件驱动的消息链路 | 小车的消息先到 IoT Hub，再触发 Functions 处理，结果存进 Cosmos DB，指令再发回小车，指令 30 秒内没确认算超时。关键概念：消息分区（partition）、读到哪了的记号（checkpoint）、至少送达一次（可能重复）、防重复处理的编号（幂等）。 | 能讲清这几个概念，并指出项目里哪些没有实现。 | 3 h |
| 6 | 零信任的基本部件 | 零信任就是“内网也不默认信任”：私有网络、私有入口（Private Endpoint）、不放密码的身份（托管标识）、云端调用 IoT Hub 时的 HMAC 签名令牌（SAS），注意设备端并不校验指令内容的签名。 | 每个部件各用一句话说“防什么、不防什么”。你有 AZ-305、AZ-104、SC-300，会被深问。 | 2 h |
| 7 | 云端和边缘的取舍，以及证据缺口 | 论文在浏览器里跑了个 0.5B 的小模型，中位 59 毫秒，很快。但只测了速度，没测准不准。 | 能说“测了什么、没测什么”，并讲出补测方案：同一批 200 条场景上测它的准确率。 | 2 h |

## 简历要不要写

这一节讲什么：哪些内容放进简历，哪些先别放。

写，并放在 AI 方向简历的第一个项目。原因：它是你唯一的 AI 项目，而且“发现自己评分标准有问题并修正”正好体现你定义问题、验收结果的特点。论文是公开的，面试官可能找得到，所以简历、论文、面试三者说法不能有冲突。

简历里的这一条已经改成白话：用 200 个模拟场景测试，约四成（79 个）不必走完三步就能给出结果，完整三步平均约 6.2 秒；发现“危险”的判定标准与系统实际规则对不上，先修正标准，再把“判断对不对”“最终动作”“响应速度”分开评价。

| 写进简历（论文里都能对上） | 先不写（原因，白话） |
| --- | --- |
| 三阶段流程和提前退出 | Router 94.19%：它是对着后来被你查出有问题的旧标准答案打的分，和“评分标准有问题”放在一起会自相矛盾。 |
| 200 个场景中 79 个（39.5%）不必走完最后一次模型调用 | 关键障碍检测 86.8% 和漏判 13.2%：论文里同一个指标有两个口径（86.8% 按最终动作，图里的 81.6% 按第三步之前），论文没写清，简历不用。 |
| 完整三步平均约 6.2 秒（121 个完整样本），动作编译约占一半 | “每次提前退出节省 N 毫秒”：是推算出来的，不是实际测的。 |
| 发现标准答案与系统规则不一致，并分开评价 | 边缘 59 毫秒、“小于 200 毫秒”、“快 31 倍”：只测了速度，没测准确率。 |
| Azure 私有网络部署（Bicep、Hub-Spoke、私有入口、托管标识） | 零信任测试的百分比：论文没写每项测了多少次。 |
| 结论与分工：云端做理解和留痕，紧急停车在本地；数据是模拟的，结论是诊断性的；说明 AI 助手的使用边界 | “validated blueprint”“provable”“to our knowledge the only work”这类说得太满的话；点云、联邦学习；成本估算。 |

## 面试准备

这一节讲什么：9 个最可能被追问的问题。右边只给思路，用你自己的话说，不要背稿；每题答完，要能再往下答一层。

| 面试官问 | 你可以这样说（口语版） |
| --- | --- |
| 五分钟介绍这个项目 | 先说问题：消息处理成功，不等于动作来得及。再说做法：小车的数据走云端，三个模型接力判断，另外单独有一条本地的紧急停车路径。然后说为什么：速度乘延迟，云端一圈要 6 秒，车早就冲过去了，我也承认这是简化模型。给一个带分母的结果：200 个场景里 79 个提前出结果，完整三步平均约 6.2 秒。最后讲我发现标准答案和系统规则对不上，是怎么改的。 |
| 这个项目你自己写了多少？ | 直接说：大量使用了 AI 编程助手。然后说我做了什么：定义问题、在 Azure 上部署试错、用测试和原始结果去验收、发现并纠正 AI 写出来的没有证据的结论。最好再举一个具体例子。 |
| 为什么一开始没有评测？ | 如实说：我先做的是应用和可视化，当时没想到要评测。写论文时才跑了 200 场景，跑完之后审查，才发现标准答案和系统规则不一致。所以我现在的习惯是先定义怎么评测，再去跑模型。 |
| 你的三智能体在关键指标上不如一句话的基线，为什么还做？ | 基线只回答一个是非题，所以那个指标高。三智能体多了可审计的记录、提前退出和按租户设策略，代价是中间多一次交接，会丢信息。两次测试抽到的场景不一样（基线那次 44 个危险场景，三智能体这次 38 个），指标口径也不完全一样，不能直接说谁更准。我学到的是：安全相关的判断，先用最简单的硬规则做基线，再证明复杂方案值得。 |
| 论文里 13.2% 的关键障碍漏判是真的危险吗？ | 要看口径。按“最终动作是否含停车或阻断”算，38 个危险场景里漏了 5 个（13.2%），这 5 个的距离是 30、34、34、40、46 厘米，全在系统 30 厘米规则之外，是旧标签把 5 到 50 厘米都算危险造成的；按“进入第三步前是否被拦住”算，漏了 7 个，论文的图用的是这个口径。我会先说清口径再引用。论文自己也写了 20 到 40 厘米之间的标签带有主观阈值。后来的 60 场景诊断里，5 个分歧点都在 30 厘米以上，最终动作都含停车，30 厘米以内的 8 个全部拦住了。 |
| 边缘模型 59 毫秒够快，准确率呢？ | 我只测了速度（中位 59 毫秒，20 次，最慢 431 毫秒），没测准确率，论文也这么写了。下一步是在同一批 200 条上测它分得准不准。测之前，不能说它补上了安全缺口。 |
| 0.21 m/s 的临界速度怎么理解？ | 它是 1.2 米的刹车距离除以 5.68 秒的中位延迟，假设刹车距离不变，是个保守的简化，实际上刹车距离随速度的平方增长。重点不是 0.21 这个数，而是 2.5 m/s 的车在一次 6 秒的云端往返里，会走过远超刹车距离的路，所以紧急停车必须放在本地。 |
| 15、20、30 厘米三个阈值是怎么回事？ | 如实说：代码里实际有两个。15 厘米是线上链路里唤醒云端的门槛，30 厘米是安全规则（写在 Safety 的提示词里），两个没有统一。20 厘米只在设计文档里出现过，代码里没有实现。论文的教训 4 自己也提到：2.5 m/s 下 31 厘米只要 124 毫秒就到了，固定阈值有盲区，建议改成按速度和延迟算的动态阈值（还没验证）。重做的话我会把它们写成一份带版本号的配置。 |
| Azure 现在还在跑吗？ | 真实部署过，是企业式环境，含私有网络，后端跑在 Container Apps 上。最早我用 Azure Functions 和 Event Hub 在本地做了事件响应测试，后来重心转到模拟 AGV 行动，这部分就撤掉了，所以最终部署里没有，论文里写的链路比实际部署多一段。学生账号额度用完后停了；之后的试用账号没有 AI 额度，所以现在没有在线环境，留下的是 Bicep 模板和试错记录。 |

**这次查出的两个需要主动说的问题**（别等面试官发现）：

- 线上链路里，障碍距离在 15 到 30 厘米之间时不会唤醒云端，所以 30 厘米的安全规则在这段距离内用不上。评测跑的是另一条路径，没有这个门槛。
- 30 厘米这条规则是写在 Safety 的提示词里、让大模型比较的，不是代码里的硬判断。论文的教训 1 恰恰说关键规则要放进代码。两者有矛盾，要自己先说出来。

**Azure 部署核对结果**（Gemini 查 Bicep 和部署记录）：

- Hub-Spoke 两个虚拟网络和双向对等互连：属实。
- Private Endpoint：只有 Storage、Cosmos DB、Key Vault 三个。IoT Hub 走公网加连接串，没有 Private Endpoint。简历已改成实际的三个。
- 托管标识：用户分配类型，挂在后端 Container App 上，并被授予 Key Vault 和 Cosmos DB 的角色。属实。
- 后端实际托管在 Azure Container Apps，模板里没有部署 Functions 服务，也没有独立的 Event Hubs（用的是 IoT Hub 内置的 Event Hub 兼容终结点）。简历里的 Functions、Event Hubs 已改掉。你确认过：它们只在本地做过事件响应测试，后来撤掉了。
- HMAC：只是云端请求 IoT Hub 时的 SAS 令牌签名；设备端收到指令后不校验任何签名。所以不要说“指令有 HMAC 签名防伪造”，论文里如果这样写了，面试里要主动更正。
- 真实部署：2026-07-02 至 07-06 有 Azure CLI 输出和资源清单，最后一次改 Bicep 是 2026-07-06（提交 601a271）。“真实部署过”有证据。

**安全提醒**：项目里的 local.settings.json 保存了一次旧部署的 IoT Hub 管理密钥，部署记录里有订阅 ID。论文里的仓库地址是公开的，请检查这些文件是否提交到了仓库（包括历史提交），如果是，把对应的 IoT Hub 删除或重新生成密钥。

## 面试口径（2026-11-15 代码核实后）

这一节讲什么：简历已经按代码改定，这里记面试里该怎么说、不该怎么说。

- **结构**：3 个模型角色（路由、安全检查、动作编译）加 3 个代码环节（输入校验、规则收紧、动作卡口）。路由判定停车就短路，后两个模型不再调用。不要说“四层”“三智能体全链路已评测”。
- **数字的范围**：300/300、70/300、55/55 只对应路由加规则层。安全检查和动作编译没进正式评测，完整 HTTP 流程只在假模型和假数据库下测过（LIMITATIONS.md 第 19 条）。
- **边缘端**：代码里没有。车端只发遥测、打印指令；30cm 是云端规则里的仿真约定。面试说成“设计结论是立刻响应的动作应该在车端本地闭环，本项目没实现”。边缘小模型的 59 毫秒只测了速度，没测准确率。
- **多模型**：只是配置层可切换提供商（OpenAI 兼容接口），正式评测只用过 DeepSeek。不要说“适配多个模型”。
- **JSON**：没用函数调用或 JSON 模式，在提示词里要求只回一个 JSON，再用严格解析器校验（prompt.py 的 parse\_reply），不合格按解析失败停车。这是可以讲取舍的点。
- **测试集**：提示词只有一次提交，早于测试集冻结；清单记有哈希；开发集那轮没有分类错误可调。可以说留出集。但只验证了一个提示词版本和一个模型家族，没有第三方审计。
- **标注**：盲评已执行，但是 AI 标注加 AI 复审，κ=1.0 只说明自洽，不是人工专家标签。不引用 κ 作质量证据。
- **基线**：R1 漏停 14、R2 漏停 10，是两套固定关键词规则，不是同一系统的优化前后。R1 备注状态 49 个错误中 39 个是险情被判成无关（符合关键词没命中的特征），但 14 次漏停逐条原因没分析过，不说“语义盲区”。
- **消融**：没做不带规则的模型单独跑。被问“那要规则干什么”时，用设计理由回答：紧急动作不能依赖模型；输入校验拦下 13 例非法输入；接口故障时规则兜底（开发集遇到 5 次接口错误）。注意 10 例故障是本地注入，不是真实接口故障。
- **gate()**：正确顺序是模型先判，规则 gate 在模型返回后收紧。rules.py:91 的注释写“在 router 被询问之前停车”与实际不符，源码已冻结未改，建议在 LIMITATIONS.md 加一条说明。

## 90 秒主干与 6 条追问（按代码核实后的修正版，2026-11-15）

这一节讲什么：Gemini 给的面试框架结构可用，但有几处超出事实。这里是用已核实内容改过的版本。练的时候只记数字和三个源码位置，话用自己的。

**三个源码位置（30 秒内能说出）**：`check_input`（router\_v2/rules.py:162）在模型之前拒绝非法输入；`parse_reply`（router\_v2/prompt.py:73）严格校验模型 JSON，不合格即停车；`execute`（router\_v2/rules.py:181）合并遥测算出的风险与模型给出的风险，模型删不掉代码算出的风险。行号以当前版本为准。

### 90 秒主干（四步）

1. **结论（10 秒）**：OmniGuard 是我在 Azure 上部署的 AGV 仿真智能体决策与评测系统，解决传感器数据加操作员自然语言备注混合输入下的安全路由。在 300 条冻结的合成测试集上，两套关键词规则基线的高危漏停分别是 14 次和 10 次，本方案是 0 次；55 例压力用例全部按预期完成。
2. **为什么需要（15 秒）**：只靠写死的关键词规则，备注里的险情容易漏；全交给大模型，接口超时、限流、返回格式错就会失控。所以要让模型做语义判断，让代码守底线。
3. **怎么做（45 秒，按请求进入系统的顺序讲）**：先由 `check_input` 在调模型前拒绝非法输入；再由路由模型把数据分到 6 类状态，判定需要停车就直接短路，不再调后面两个模型；模型回复用 `parse_reply` 严格校验，任何一步不合格按解析失败停车；最后由 `execute` 合并代码算出的风险和模型的判断，障碍距离低于 30cm（仿真约定）一律停车。
4. **证据和边界（20 秒）**：提示词只提交过一次，早于测试集冻结，清单记有哈希；评测对象是路由与规则层；安全检查和动作编译只在假模型下测过。

### 追问 1：300/300 是不是对着测试集调过提示词？

测试集是合成的，6 类各 50 条，另含 72 条备注（6 种备注状态各 12 条）。提示词只有一次提交，早于测试集冻结提交；清单记了提示词和数据的哈希；开发集那一轮没有分类错误可供调参，所以可以说留出集。局限也要说：只验证了一个提示词版本和一个模型家族，没有第三方审计，标注是 AI 标注加 AI 复审，不是人工专家标签。关键词基线 R1 在同一测试集上错 19 条（漏停 14、误停 3、另 2 条类别混淆车仍停），R2 漏停 10、误停 6；这说明测试集不是简单到所有方法都满分。

### 追问 2：漏停降到 0 是模型的功劳还是规则的功劳？做过消融吗？

没做不带规则的消融，所以不能说各自贡献多少。我也没有逐条分析那 14 次漏停的原因；能确认的是 R1 在备注状态的 49 个错误里，39 个是险情被读成无关，符合关键词没命中的特征。保留确定性规则的理由是设计上的：紧急动作不能依赖模型；`execute` 保证代码算出的风险不会被模型删掉；接口故障时模型回不来，要由代码停车。开发集里实际遇到过 5 次接口错误。

### 追问 3：JSON 约束是用的 Structured Outputs 还是 Pydantic？

都没用。没用 `response_format`、JSON 模式或函数调用，是在提示词里要求只回一个 JSON，再用手写严格解析器 `parse_reply` 校验：必须是单个 JSON 对象，键恰好是 `primary` 和 `note_status`，不能有代码围栏或多余文字，不能有重复键，取值必须在 6 类和 6 种备注状态里，不合格按解析失败停车。取舍：不依赖 SDK 特性，换模型提供商更容易，代价是格式遵从完全靠提示词和事后校验。

### 追问 4：55 条压力用例里 23 条没有用量记录，是失败吗？

不是失败。55 条是 11 种类型各 5 条。其中 13 条是非法输入，在 `check_input` 就被本地拒绝，没有发请求；10 条是注入的超时和限流故障（类型 10、11），也不调模型。真正发给模型的 32 条来自类型 3 到 8（边界小数、多风险冲突、备注与遥测来源不一致、中英混合并含错别字的备注、多子句含否定历史假设、备注里的提示注入，各 5 条）加类型 9 里的 2 条合法输入。要讲的是类型覆盖，每条具体内容在私有数据里，不要说得比这更细。

### 追问 5：6 类还是 8 类？

业务状态是 6 类：NORMAL\_NAV、CRITICAL\_OBSTACLE、LOW\_BATTERY、OVERHEAT、LOW\_HEALTH、OVERSPEED。非法输入和故障停车是工程层的处理，不属于模型分类空间，也没有放进测试集的 300 条分类里。

### 追问 6：安全检查和动作编译为什么不测？有什么局限？

这是项目的明确边界。正式评测只覆盖路由与规则层。安全检查和动作编译有完整代码，也有 `validate_actions` 卡口，但只在假模型和假数据库下测过集成（LIMITATIONS.md 第 19 条）。不要用“有短路所以不用测”来解释：短路只发生在需要停车的请求，其他请求仍会调用后两个模型。其他局限：30cm 是云端规则里的仿真约定，车端模拟程序只发遥测，没有制动逻辑；正式评测用的是 DeepSeek，没有在 Azure OpenAI 上验证；没做消融。如果上真车，下一步是把立刻响应的动作放到车端本地，并引入人工专家标注。

### 补充：故障怎么处理的（别说成“后置规则单独接管”）

适配器把异常转成故障值（超时、限流、接口错误），再交给 `execute`，由它直接停车并记下故障名。“100%”只对 10 例本地注入故障成立，是本地模拟，不是真实接口故障。这个机制只覆盖路由那次调用；安全检查和动作编译走旧路径，异常由外层捕获成内部错误并停车。

### 补充：Azure 和 DeepSeek

Bicep 描述的是 Azure 基础设施（含 Key Vault 和 OpenAI 参数，端点是占位符），模型提供商通过配置切换，正式评测只在 DeepSeek 上跑过，没有在 Azure OpenAI 上验证。被问到“Azure 上为什么调 DeepSeek”就这样答。
