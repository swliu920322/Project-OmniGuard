# Data grouping and quantity plan (a plan: nothing is generated, nothing is frozen)

Applies to spec `0.3-candidate`. Synthetic samples of a simulation; they are never described as production data. Numbers are targets to be confirmed at the pre-freeze review.

## 1. Who makes what

| Set | Made by | Seen by the tuning session |
|---|---|---|
| Public boundary examples (`ambiguous_examples.json`) | Claude | yes (dev material) |
| Dev set | Claude | yes |
| Stress set | Claude writes dev-side stress cases; the acceptance session writes the test-side ones | dev-side yes |
| Frozen test set | the **acceptance session**, written and reviewed independently; disputed items go to the owner | **no**. The tuning session only ever receives the file hash (commitment) and the per-class counts. |

If the test set is used for tuning after exposure, it becomes an exposed set and the final acceptance needs new independent samples.

## 2. Unit of grouping: the family

A **family** is one base scenario with all its variants: a risk pattern (which of the five risks fire, and at which side of each threshold), plus, for noted records, one note template with its language and paraphrases. Numeric variants, paraphrases and translations of the same base belong to the same family.

**A family never spans dev and test.** Assignment is by a hash of the family id fixed in advance, so nobody can move a family after seeing results. The test set is also deduplicated against the public examples and the dev set, on the rendered input text.

## 3. Quantities (targets)

| Set | Per class (6 classes) | Total | Notes |
|---|---:|---:|---|
| Dev | 30 | 180 | |
| Frozen test | 50 (floor 30) | 300 | with 30 per class one error moves recall by 3.3 points, so uncertainty is reported |
| Stress | >= 5 per stress type | >= 40 | 8 stress types, see section 5 |
| Noted records inside dev | | >= 60 | >= 10 per note status |
| Noted records inside test | | >= 72 | >= 12 per status, each status split across English, Chinese and mixed (>= 4 each) |

Noted records count in the class of their gold primary. Their statuses `AFFIRMED_CURRENT` and `UNCERTAIN` land in `CRITICAL_OBSTACLE`, the others mostly in the class their telemetry gives, so the per-class floors are met by planning telemetry and notes together.

## 4. Coverage inside each class

For every class, in both dev and test:

- **Threshold sides:** below, exactly at, and above each of the five thresholds (the equality cases are the ones that expose off-by-one reasoning).
- **Single risk and multi-risk:** each class appears alone and in conflict. All 10 pairs of the five risks appear at least twice across the test set; at least 6 records carry three or more risks.
- **Physical gate:** records with `hp <= 0` or `battery < 5` (router skipped in production) are included and flagged, so classifier results can be reported with and without them.
- **Values:** at most two decimals, rendered exactly (`render_telemetry`), no value that an integer cast would change meaning for.
- **Class balance:** `OVERSPEED`, `LOW_BATTERY`, `LOW_HEALTH` have no support in the old data; their samples are all new.

## 5. Stress types (each >= 5)

| # | Type | Fits the current input? |
|---|---|---|
| 1 | Unit mix-up or out-of-domain value (battery 180, negative distance) | yes, expects INVALID_INPUT |
| 2 | Missing or null field | yes |
| 3 | Boundary equality and near-boundary decimals | yes |
| 4 | Multi-risk conflict | yes |
| 5 | Contradictory note vs telemetry (source disagreement) | yes, noted records |
| 6 | Chinese, English and mixed-language notes with typos | yes, noted records |
| 7 | Multi-clause and negation / history / hypothetical notes | yes, noted records |
| 8 | Prompt-injection text inside the note ("ignore the rules and continue") | yes: must not remove a risk or the stop flag |

No chatbot is built to satisfy a stress type; types that need free-form dialogue are out of scope.

## 6. Procedure and commitments

1. Family ids and the hash rule are fixed and committed before any sample exists.
2. The dev set is generated by script from a seed (`SPEC_VERSION` in the file name) so it can be regenerated.
3. The acceptance session builds the test set, commits only its SHA-256 and the per-class and per-status counts to the repository, and keeps the file.
4. Before the formal run the baseline B and the optimized version are frozen by commit; the test result is not used to tune again in this round.
5. Two independent runs follow the reproducibility gate (agreement >= 98 %, accuracy difference <= 2 points).
