# Known limitations (kept up to date; last change 2026-11-21)

Written so that nothing is discovered later and quietly left out. Items 1 to 16 were known before or during the formal run, items 17 to 20 were added at wrap-up, items 21 to 26 after the second round.

## About the task and the data
1. **A simulation.** All thresholds, priorities, actions and the turn range are experimental conventions of a cloud-edge AGV simulation. None comes from real equipment, a standard or field data.
2. **Synthetic and templated data.** The 180 dev records are generated by rules from a seed. The 72 notes are templates in three languages with numeric variants, not 72 independent scenarios. A model that reads the rules written in the prompt can do very well on such data (baseline B: every reply that came back was correct), so the dev set separates little. Whether the independent test set separates more is not known yet.
3. **AI labels, not expert truth.** The dev notes have now been blind-annotated on 33 of 96 noted items and all 96 reviewed. The final test notes have a sealed 24/72 blind sample and all 72 reviewed; all 20 noted test-side stress cases were independently annotated and reviewed. The blind samples agreed with the initial statuses, but both annotators are AI sessions and can share misreadings. High agreement establishes consistency with the specification, not external correctness. Test records form 34 conservative families; 300 records must not be described as 300 independent scenarios. Mandatory threshold/gate anchor designs are shared with dev by specification; other backgrounds and note scenarios were independently authored and audited. See `acceptance/FROZEN_MANIFEST.json`.
4. **Gold routes are rules.** Telemetry labels are computed by the specification's rules, so on telemetry-only records a rule reproduces the gold by construction. Agreement with the gold shows consistency with the written convention, not correctness against an outside truth.
5. **Old data is history.** The archived 200 rows (baseline A) have no independent support for `LOW_BATTERY`, `LOW_HEALTH` or `OVERSPEED` (all 51 old sensor-error rows are overheating) and 11 old "critical" rows sit at 30 to 50 cm. Baseline A's 96.5 % / 78.0 % describe the original implementation's router stage only, with legacy labels, and are not comparable with the historical 94.19 %.

## About the model and the measurements
6. **The model version is unverified.** The API returns only an alias (`deepseek-flash`); the configured name `deepseek-v4-flash` is no longer in the provider's model list. The version in every record is the owner's statement.
7. **A reasoning model.** It spends hidden reasoning tokens and ignored `max_completion_tokens=20`. Cost and latency include them. The requests carry `temperature=0`, but the provider documents that its default reasoning mode ignores temperature, so the temperature is **not** demonstrably controlled; reproducibility rests on the two-run agreement gate, not on the setting.
8. **Provider errors are part of the numbers.** Baseline B's dev run had 5 failed calls of 180 (four HTTP 500, one 503); they count as wrong and are not retried. Two baseline-B canaries failed with HTTP 500 and a later diagnosis could not tie the failures to any change in the request; the cause is not established (a service incident was showing on the status page, which makes a service-side cause plausible, not proven). The formal policy was fixed in advance: no retry, failures counted wrong, a success-only accuracy only next to the main figure. The formal programme observed no provider error in 634 calls; that does not establish future availability.
9. **Costs are estimates, not bills.** See the ledger in `EVIDENCE_INDEX.md`.

## About the backend path
10. **Fake dependencies.** The opt-in extended tenant's HTTP flow (Router, Safety, Compiler, action contract) is tested with fake models and a fake Cosmos. It has not been run end to end against a real model through the endpoint. (Since 2026-11-21 Safety and Compiler have also run once against the real model on 84 records with the Router replayed from sealed replies; see item 26. The Router stage of that run was not a live request.)
11. **`goal=CHARGER` is a structured goal.** Nothing checks a path or a destination; it is not evidence that a vehicle reaches the charger, and "return to charge executed" must not be claimed.
12. **The physical gate differs between paths.** The legacy path uses the endpoint's integer values; the extended path uses the evaluation's gate on the exact values. The IoT Hub path is not switched.
13. **The emergency stop is a flag.** It is a structured boolean from a separate entry, not something recognised from text; there is no real stop channel behind it in the simulator.

## About the rule controls
14. **R1 and R2 are weak baselines with disclosed failures**: the subject of a clause cannot be carried over ("刚才有人，现在走了"), and typos defeat the keywords (one missed halt in the dev stress cases). Their word lists were written by the author of the dev notes and extended once on the public examples; their dev numbers are offline results on dev material, not formal results and no evidence of generalisation.

15. **Observed formal results are bounded by the synthetic set.** Both main runs returned 300/300 correct primary labels and 72/72 note statuses; the 55-case stress set had no observed missed halt, needless halt or model error. This is consistency with spec 1.0 on these samples, not industrial safety or general language robustness. The reported Wilson intervals are record-level, not adjusted for 34 families.
16. **One raw stress counter includes offline cases.** `calls_without_usable_usage=23` counts the 23 stress rows that never called the API. All 32 real stress requests reported usage. The original result is preserved and `formal/results/VERIFICATION.json` supplies the interpretation; costs and scores are unaffected.

17. **The formal numbers of round 1 cannot be reproduced from the public repository.** The frozen test and stress files were private (hashes and counts are public), and as of 2026-11-15 they can no longer be found (item 22), so the paid level-3 reproduction cannot be done now. A stranger can still check the integrity of the published files, rerun everything offline, and rerun the pipeline on the public dev set with their own key. Round 2 is different: its questions and replies are public, so its numbers can be recomputed for free. See [REPRODUCE.md](REPRODUCE.md).
18. **The test set barely separates good systems.** B-1.0 is at the ceiling on the dev set and on the frozen set, so these data cannot rank prompts or models that are all close to correct; they do separate the keyword rules (281/300 and 280/300, with 14 and 10 missed halts). Comparing models or prompts needs harder, independently written data, and a new untouched test set once this one has been used.
19. **Verification by the tuning side is limited to what is public.** Records, replies and per-record errors stay in the private package; the tuning side checked aggregates, hashes and the independent recount in `formal/results/VERIFICATION.json`, not the private files themselves.

20. **Safety and Compiler can make the Router's decision stricter, but they do not look for risks the Router missed.** Two comments in `embodied_brain/extended.py` said Safety and Compiler "may only make the result stricter". That is true in one sense (they cannot loosen the decision) and easy to misread in another (that the system never misses a stop). On 2026-11-21 the comments were reworded to say exactly that. What the code does guarantee: the model cannot cancel a telemetry risk the code found, nor the emergency-stop flag or the physical gate; the code adds any telemetry risk the reply did not name and checks the Compiler's actions against the decision. What it does not guarantee: a risk that comes only from the operator note depends on the model's reading of the note, so a wrong reply (for example `IRRELEVANT` for a note that reports a person ahead) can still miss a stop. The rule baselines R1 and R2 show the same limit with their missed halts. Latency and cost evidence: [LATENCY_COST.md](LATENCY_COST.md).

21. **The `gate()` comment, and which code path asks the model first.** `router_v2/rules.py` line 91 says the physical gate (HP <= 0 or battery < 5) "halts the vehicle before the router is asked". There are two code paths. (a) `decide()` in `router_v2/pipeline.py`, the frozen function the evaluation measured, calls the model first and applies the gate afterwards in `execute()`, so a gated record still costs one model request there (the test `assert gated['model_called']` in the code guide shows it); the comment is not true for this path, and the file is frozen, so the comment stays. (b) The HTTP flow in `embodied_brain/extended.py` has checked the gate before asking the model since 2026-11-21, so a gated request makes no model request; the comment is true there. For a gated record the HTTP decision is the code's alone: the same motion (HALT) and the same telemetry and gate reasons as path (a) when the model adds nothing, but a risk that only the model would have added (for example from an operator note) is not in the reason list, and the decision records `model_called: false` and `gate_skipped_model: true`. The formal numbers come from path (a) and are not affected. Tests: `tests/test_extended_endpoint.py`.

22. **The private test data and per-record run logs are no longer on this machine (checked 2026-11-15).** The frozen `test_set.jsonl`, `stress_cases.jsonl` and the record-level run directories were kept outside the repository under `/private/tmp`; those directories are now empty and no copy was found in the readable parts of the repository history, the home directory and the agent conversation logs. **The search is not complete:** the macOS trash (`~/.Trash`) and the OneDrive folders were refused by the system ("Operation not permitted") and were not checked, and backups on other devices were not checked. The creation of two archives of them (and their SHA-256) is recorded in the Codex session log, but the archives themselves were not found; why they went is not confirmed (the temporary directory may have been cleaned automatically, unverified). Consequences: level 3 reproduction (rerun on the original questions) and any per-record error analysis (for example which of R1's 14 missed halts were threshold, keyword or meaning problems, and whether they match the 15 note misreadings) cannot be done now, and that correspondence stays unverified. What still holds: the published summaries, hashes and aggregate numbers are intact and pass `shasum -c`, which shows the saved files match the manifest; without the originals the underlying scoring and the causes of individual errors cannot be re-checked. Read the numbers accordingly: `floor_override` 70/300 counts how often the code added a risk or a restriction to the model's reply, not 70 model mistakes rescued; 55/55 is a mixed check of which only 32 were real model requests. If the archives turn up, verify them against the recorded hashes before use.
23. **Who annotated, and from which model family, was not recorded in the data files.** Added 2026-11-21 from session self-reports and git, not from the original records alone. Round 1: the test-set author, the blind annotator, the reviewer, the adjudicator and the custodian were all GPT-family sessions (separate sessions); only the specification implementation and the rule control came from another family, so agreement between annotators is not cross-family evidence. Round 2: the author was a Gemini session and the blind annotation and review were GPT-family sessions, so writing and labelling came from different families; the author also committed part of the process records and read reviewer opinions and adjudication reasons, but not the blind results. The GPT custodian also edited the rationale validator it used for acceptance. Model strings come from run records, not weight verification. A metadata extract of the exported sessions (`eval/provenance/SESSION_META.md`) confirms the model strings and which session issued which commit; what a session saw (for example whether a blind annotator was told who wrote the items) rests on that session's own account. Commit trailers (`Co-Authored-By`) do not prove who wrote a commit. Details and open points: [ANNOTATOR_PROVENANCE.md](ANNOTATOR_PROVENANCE.md).

24. **The Safety and Compiler calls of the extended flow changed after both formal rounds (2026-11-21).** They now use `embodied_brain/bounded_agent.py`: one request, SDK retries off, a 60 s timeout (a placeholder equal to the Router's; no latency of these two roles has been measured), no result cache, and a classified fault (TIMEOUT / RATE_LIMIT / API_ERROR / BAD_REPLY) that becomes a stop instead of INTERNAL_ERROR. Before, they used `ask_agent` with the SDK defaults (2 retries, 600 s read timeout, checked offline with openai 2.41.1). One behaviour change to know about: an empty Safety reply used to read as PASS (only a reply starting with BLOCK stopped the vehicle); it is now a BAD_REPLY stop, and an empty Compiler reply was already a stop. With a reasoning-mode model and `max_completion_tokens` of 50 or 100 a reply could come back empty, so the new path might stop more requests than the old one. In the real run of item 26 no reply came back empty (0 of 168 requests), because the provider does not cap the output at that bound (item 25). The change is covered by fake-client tests and by that one real run; neither the formal runs nor the historical latency figures used the new path. `router_v2` and every frozen file are unchanged. See [DESIGN_BOUNDED_RETRY.md](archive/designs/DESIGN_BOUNDED_RETRY.md).

25. **The provider does not honour `max_completion_tokens` on the Safety and Compiler requests (observed 2026-11-21).** The first real health check of `eval/safety_compiler/` (run `20261121T134755Z_real_b0c7fc4b`, sealed) sent one Safety request with `max_completion_tokens=50`; the reply was `PASS`, but the usage was 213 prompt and 80 completion tokens, 77 of them reasoning tokens, so the output bound was exceeded and the runner stopped as designed. This is the same behaviour item 7 recorded for the Router at `max_completion_tokens=20`. Consequences: that parameter is not an output cap for these two roles with this provider (in the legacy `ask_agent` path either); the budget model that reserved 50 output tokens per call was wrong; and the worry that a small `max_completion_tokens` would cut the reply to nothing did not show in this one request. The stopped record shows `FAULT/API_ERROR` for Safety only because the run's own stop interrupted the call, not because the provider failed. One request, 293 tokens and about US$0.0002 were used of the confirmed 180 / 250,000 / US$0.10. Fix (same day, no model request): the runner now reserves 2048 output tokens per request for the budget (the Router runs' bound) and stops if a request reports more; every earlier real run counts against the same total; the interrupted record carries a note. The production request is unchanged (no `max_tokens` was added), so `bounded_agent.py` still does not cap the output of these two roles with this provider.

26. **One real run of Safety and Compiler (2026-11-21): availability and latency only.** Run `20261121T140117Z_real_c75ee025` (sealed, in [safety_compiler/runs](safety_compiler/runs/)): the Router was replayed from the sealed round-2 replies, 84 records reached Safety (the others halt before it), and each got one Safety and one Compiler request through the real extended flow: 168 requests in all, no retries. Result: every request returned usable text; Safety passed 84 of 84 and blocked none; the Compiler's actions passed the code-layer contract 84 of 84 with no violation; no empty reply, no fault. Latency from the endpoint metrics: Safety median 1.2 s (P95 2.2 s), Compiler median 1.7 s (P95 3.6 s). Use: about 63,000 tokens and US$0.049 estimated; with the earlier health checks 177 requests of the confirmed 180, about 66,000 of 250,000 tokens and about US$0.052 of US$0.10. The provider did not honour the requested output bounds: Safety exceeded 50 completion tokens on 81 of 84 requests (median 86, maximum 500) and the Compiler exceeded 100 on all 84 (median 198, maximum 596). **This is not a safety evaluation.** Safety passing everything shows only that it blocked none of these 84 records; there is no gold label saying which should be blocked, and the real Compiler never produced an output the code layer had to reject, so that layer was not exercised by a real failure. The records are synthetic (28 per language, three writings of one situation), one model, one run; the timeout of 60 s is still a placeholder. The stored `started_at` of the run is the time the files were written, not the start.
