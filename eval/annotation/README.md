# Annotation materials (rehearsal of ANNOTATION_PROTOCOL.md on dev material)

What is here: the 96 noted dev items (72 dev-set notes + 24 dev stress notes of types 5-8) under opaque shuffled ids `A001`..`A096`; the seeded, stratified blind sample (33 items, 34.4 %, at least 4 and at least 30 % of every status; `blind_sample.json`, ids hashed); the blind packet (`blind_packet.jsonl`: the input text only) and `ANNOTATOR_INSTRUCTIONS.md`. Nothing labelled is released: the review packet with the author's labels is written only by `packets.py release`, which refuses until the blind session's results are **sealed and committed**, and refuses to write inside this folder.

**Order (protocol steps 3 to 6).** 1. This folder is built and committed (the sample ids are hash-committed). 2. A second session, given only `blind_packet.jsonl` and the instructions, returns `blind_results.jsonl`. 3. `python eval/annotation/packets.py seal <file>` validates it (exactly the sample's ids, legal statuses, clause statuses that combine to the note status, non-empty bases) and writes `sealed/`. 4. Commit `sealed/`. 5. `packets.py release --out <path outside the repo>` gives the reviewer the initial labels. 6. The reviewer's `review_results.jsonl` goes to `packets.py report`, which writes `agreement_report.json`: agreement before adjudication (raw and kappa, or "undefined" with the reason) for the blind sample, the review change rate (not an agreement figure), and the items that go to the owner.

**Status:** steps 2 to 6 have not been run. The dev note statuses are still the generator's provisional labels. The isolation of the blind session is procedural (it is handed two files); the dev labels exist elsewhere in this repository. For the test set the acceptance session holds its data privately and uses the same tools. AI annotation and AI review, never described as human expert labels.
