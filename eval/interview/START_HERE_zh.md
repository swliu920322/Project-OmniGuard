# 从这里开始：先看懂一辆小车的一次决定

这页不要求先懂英文、模型或后端。先用中文走完一个例子，再把中文与代码名字对应。所有例子是教学示意，不是正式测试记录。

## 1. 系统收到的是什么？

想象电脑里的一辆搬运小车，上报了一张读数表：

| 读数 | 示例值 | 大白话 |
|---|---:|---|
| 前方距离 | 20 厘米 | 离障碍还有多远 |
| 当前速度 | 1 米／秒 | 车正在多快地走 |
| 健康值 | 100 | 仿真里的健康分，不是真实故障诊断 |
| 电量 | 15% | 还有多少电 |
| 温度 | 65℃ | 当前仿真温度 |

这组上报读数叫**遥测**。备注则是可选的一句话，如“前面可能有人”；本例先不加备注。

系统问的不是“小车想做什么”，而是“这些读数说明小车处于什么情况，现在允许它做什么”。

## 2. 三样结果，不要混在一起

按本实验规定，距离小于 30 厘米算障碍危险、温度高于 60℃算过热、电量低于 20% 算低电量。因此本例有三个问题。

| 结果 | 本例内容 | 有什么用？ |
|---|---|---|
| **全部风险清单** | 障碍、过热、低电量 | 不遗漏同时存在的问题 |
| **主要状态**，也叫主标签 | 障碍 | 在多个问题中，用一个名称概括最优先处理的问题 |
| **当前动作与附加要求** | 停车；保留冷却要求；把回充记为后续待办 | 避免同时下达“停车”和“立即开去充电”的矛盾要求 |

代码把“主要状态”写成 **`primary`**，把“全部风险清单”写成 **`risk_set`**，把“动作决定”写成 **`action`**。先理解中文，英文只是查代码时对应的名字。

**不是一个问题处理完再处理下一个，而是先找齐问题，再一次性决定当前允许做什么。** “回充待办”目前只是保留的信息，没有自动排队执行的回充流程；“冷却要求”也不表示已控制真实冷却设备。

主标签按本实验规定的顺序选：障碍→过热→低健康→低电量→超速。这个顺序不是工业标准。全部风险仍保留，选了障碍不代表过热和低电量消失。

## 3. 模型判断和代码检查有什么区别？

模型看遥测与备注，回答“主要是什么状态，备注说的是什么情况”。代码也会自己按数值规则计算风险，再决定动作。

还是刚才的例子，假设模型答错，说“正常”：

```text
模型回答：正常
代码检查：距离 20 厘米、温度 65℃、电量 15%，三个问题还在
最终决定：停车，保留冷却要求和回充待办
评测计分：模型的主要状态答错；动作经过代码处理后仍要求停车
```

所以“模型判断正确”和“代码把动作限制住”要分别评价。代码纠正后停车，不会把模型原来的错误答案改算为正确。

这里的“停车”是**返回停车决定**。不代表在模型回答之前车已停下，也不代表实物车辆真的执行成功。

## 4. 备注为什么还需要模型理解？

让所有数值恢复正常，只改变备注：

| 备注示例 | 应理解为什么？ | 是否新增障碍风险？ |
|---|---|---|
| 前面有人 | 当前肯定 | 是 |
| 前面可能有人 | 不确定 | 是，按实验约定保守处理 |
| 前面没有人 | 当前否定 | 否 |
| 刚才有人经过 | 历史情况，没有报告现在有人 | 否 |
| 如果前面有人就绕开 | 假设条件，不是当前观察 | 否 |
| 今天要交报告 | 无关内容 | 否 |
| 刚才有人，现在走了 | 当前否定，以现在的情况为准 | 否 |

“这句备注属于哪一种说法”在代码里叫 **`note_status`（备注状态）**。它不同于小车的主要状态。例如备注是“不确定”，小车的主要状态仍可能是“障碍危险”。

假如模型把“前面可能有人”错误读成无关，并且主要状态也报正常，正常的数值里又没有障碍依据，代码就可能漏掉风险。这是目前代码限制不能覆盖的部分。

## 5. 六类、三个角色各指什么？

六类是**六种状态名称**：正常、障碍危险、过热、低健康、低电量、超速。一个模型处理角色可以识别全部六类。

三个角色是**三个处理步骤**：

| 角色的代码名 | 中文职责 | 类似什么问题？ |
|---|---|---|
| Router | 判断状态 | “现在属于什么情况？” |
| Safety | 再审规则 | “按给定规则，这个情况是否要阻止？” |
| Compiler | 生成动作格式 | “把决定写成程序能读的动作列表。” |

本项目由程序把步骤接起来，不是三个模型自由讨论。这叫**工作流编排**：规定谁先做、把什么结果交给下一步、何时结束。

本例代码已决定停车，就不再调用后两个角色。没有“障碍 Agent”“过热 Agent”“充电 Agent”各做一次任务。

## 6. 回答长什么样？

下面是一份模型回答示例，格式名叫 JSON，可以先理解成固定表格：

```json
{"primary":"CRITICAL_OBSTACLE","note_status":null}
```

| 这段内容 | 翻成中文 |
|---|---|
| `primary` | 主要状态这一格 |
| `CRITICAL_OBSTACLE` | 这一格填“障碍危险” |
| `note_status` | 备注判断这一格 |
| `null` | 本次没有备注，留空；不是“已经判断备注无关” |

程序要求恰好两格、格名正确、内容在允许范围内。这叫**输出契约**，就是预先约好的答题格式。例如多出一句解释、漏一格或重复一格会被拒绝；正常空白与换行不是多余解释，不会仅因此拒绝。

代码合成后的返回信息还会用到下面这些名字。查到再看，不用全背：

| 代码词 | 中文 | 示例／注意 |
|---|---|---|
| `prediction` | 模型原本的判断 | 模型报“正常”，即使随后被代码纠正，也保留原判断 |
| `executed` | 代码合成后的决定 | 名称里虽有 executed，也不证明实物执行成功 |
| `motion` | 当前运动方式 | 停车、移动、限速移动 |
| `HALT`／`MOVE`／`MOVE_LIMITED` | 停车／移动／限速移动 | 是允许的运动状态 |
| `goal`／`CHARGER` | 目标／充电位置 | 目标不等于已经到达，也不代表实现路径规划 |
| `holds`／`COOL`／`LOCK` | 要保留的限制／冷却／锁定 | 本例保留冷却要求；锁定只是本实验的结构化标记 |
| `deferred`／`RETURN_TO_CHARGE` | 后续待办／回充 | 记下来，不代表后台已经启动另一个任务 |
| `halt_reasons` | 为什么停车 | 如障碍、过热 |
| `speed_cap` | 是否需要限速 | 是／否标志；具体动作上限还由代码检查 |
| `added_risks` | 代码补上的风险 | 模型只报障碍，代码补上过热和低电量 |
| `floor_override` | 代码是否补充了模型没覆盖的风险或强制限制 | 不能直接叫错误率；模型只答一个主类，多风险也可能需要补全 |
| `finish_reason` | 服务为什么结束这次回复 | 值为 `stop` 表示正常结束；**不是让小车停车** |
| `{"action":"stop"}` | 最终动作列表里的一条停车命令 | 这里的 `stop` 才描述小车动作；仍不证明实际执行 |
| `PASS`／`BLOCK` | 审查通过／阻止继续 | Safety 的文字输出，不是物理动作 |

## 7. 评测：先看一个能手算的例子

**以下数字仅用于教学，不是项目成绩。** 假设 100 条记录中，90 条正常、10 条有障碍。系统全部答正常，准确率仍有 90%，却一个障碍都没识别出来。这就是为什么不能只看准确率。

换一个系统：10 条障碍中答对 6 条，漏掉 4 条；90 条正常中又把 2 条误报为障碍。可以写成表：

| 实际情况 | 回答“障碍” | 回答“正常” |
|---|---:|---:|
| 实际有障碍 | 6 | 4 |
| 实际正常 | 2 | 88 |

这张表叫**混淆矩阵**，就是把答对和不同方向的错误摊开看。

- **准确率**：全部 100 条中答对 6＋88＝94 条，即 94%。
- **障碍类召回率（recall）**：本来有障碍的 10 条里找出 6 条，即 60%，关注漏识别。
- **障碍类精确率（precision）**：报出障碍的 8 条里，6 条确有障碍，即 75%，关注误报。
- **F1**：把上面两种比例合成一项，公式是 `2×精确率×召回率÷(精确率＋召回率)`；本例约 66.7%。
- **macro-F1**：每个类别先算自己的 F1，再对类别平均，避免大量容易类别掩盖少数难类。
- **漏停／误停**：另看最终决定是否该停没停、该走却停。不能把“主标签错”直接等同于漏停，因为代码可能补回风险；也可能标签不同但都要求停车。

项目正式成绩另看 [报告](../report.md)：两次各 300/300，是 300 条合成测试、34 个家族、AI 标注与复核，不是上述教学例子。

为什么定 300？六类每类目标 50，是实验工作量与覆盖约定，不是统计上必须如此。55 例是十一类压力各五例，也不是可靠性证明。数量的完整来源与本人／AI 分工反思见 [讲述稿第 10 节](INTERVIEW_STORY_zh.md#10-后续反思为什么是-300-和-55我个人的判断在哪里)。

## 8. 延迟与数据词：看到时怎么读？

| 词 | 中文解释 | 小例子 |
|---|---|---|
| 中位数 | 把耗时从小到大排，中间的值；偶数个取中间两项平均 | 1、2、3、4、20 秒，中位数 3 秒，不是最慢的 20 秒 |
| P95 | 第 95 百分位数，用来观察较慢请求；本项目用最近秩法时取排序后第 `向上取整(0.95×条数)` 项 | 20 次请求排序取第 19 项；不是“平均延迟的 95%” |
| 端到端 | 先说从哪里开始、到哪里结束，再谈完整耗时 | 浏览器发出到收到回复，与后端函数计时不是同一段 |
| 标准答案／金标 | 评测拿来核对的参考答案 | 本项目数值答案按规则算，备注经 AI 标注复核；不代表专家确认的真理 |
| 冻结 | 在正式测试前固定文件，不能看成绩后改题改答案 | 先定 30 厘米阈值，再测；不能测完为模型改成 20 |
| 哈希 | 根据文件内容算出的指纹，用来核对是否变化 | 换一条备注，指纹通常会变；指纹相同也不证明题目设计合理 |
| 家族 | 同一基础场景的数字变体、改写或翻译 | “前面可能有人”与对应翻译并不天然是两个独立场景 |
| 盲标 | 第二位标注者先不看初始答案，自己作判断 | 先独立判断“刚才有人，现在走了”，再比较答案 |
| Wilson 区间 | 根据样本结果估计比例不确定性的一种方法 | 300/300 也不等于未来不会错；当前区间未处理同家族相关性，不能作为保证 |
| 基线 | 用来比较的固定参考方案 | R1 是关键词方案；基线 B 是完整规则提示词方案，不是成绩或产品版本 |
| 消融／方案对照 | 去掉或替换一部分，在可比条件下看效果 | 比较单次调用和三段调用；当前没做，不能说三段更优 |

## 9. 企业 harness 里的词，不用先猜英文

| 词 | 好理解的意思 | 示例（企业设计，不是当前实现） |
|---|---|---|
| 上下文 | 这次判断所需的背景信息 | 订单是什么、A 站点在哪、用户是谁 |
| 工具 | 程序允许模型申请使用的一项操作 | 查询订单、创建运输任务；不是一类意图只能配一个工具 |
| 状态机／任务状态 | 规定任务现在在哪一步、接下来允许怎样变化 | 未开始→运输中→已送达；“已创建”不直接等于“已送达” |
| 持久化 | 把信息保存到可恢复的存储里 | 服务重启后仍知道哪张运输任务未结束 |
| 幂等 | 同一请求重复到达，也按同一件事处理，避免重复副作用 | 用同一个业务请求号重发，不再建第二张运输单；需要后端支持，不是模型自己保证 |
| 补偿 | 后续失败后，对已发生的操作作业务补救 | 已预留充电位但运输取消，按规则释放预留；不一定能完全恢复原状 |
| 权限／鉴权 | 身份和允许操作范围的检查 | 能看订单不一定能取消订单；不能让模型口头决定权限 |
| trace／执行轨迹 | 记录每一步做了什么与结果 | 哪次判断、哪次工具调用、在哪停住，用来排查 |
| SDK | 帮程序调用服务的一套现成代码 | 可配置超时和重试；它可能在你只调用一次函数时内部再请求 |
| MCP | 一种连接工具与数据的协议 | 业务 API 可通过它暴露；不采用它也可以实现工具调用 |
| 接口契约／schema | 约定输入输出有哪些字段、类型和限制 | 创建运输单必须给订单号和站点；不能只写“去那里” |
| harness | 把模型、背景、工具、检查和执行步骤接起来的外围程序 | 等送达确认再安排充电，不能只因为模型说“已送达”就继续 |

前端中的 Props 是父组件传给子组件的数据和操作入口，例如传入电量、传入“点击开始后做什么”；Hook 是把状态与交互逻辑集中起来的函数，例如管理车辆位置和请求过程。这里都只是代码组织方式，不代表已经低耦合或可直接跨项目复制。
