# 业务 harness：从后端编排到可靠执行的理解

用途：把本项目的后端经验与企业 AI 应用联系起来，回答“harness 是什么”“与后端有什么区别”“通用模型怎样接业务”。本页是已有实现解释与后续设计思考，不是新增产品能力、企业部署或效果证明。

配套阅读：[Agent 与意图](AGENT_INTENT_DESIGN_zh.md)、[后端代码地图](BACKEND_CODE_GUIDE_zh.md)、[正式报告](../report.md)。

第一次接触这些词，先读 [中文入门页](START_HERE_zh.md)。本页说的“上下文”就是判断需要的背景；“编排”就是安排步骤和传递结果；“契约”就是约定输入输出的格式与限制。例如创建运输任务时，先给订单号和目的地，保存返回的任务号，等系统确认送达再继续。它不是让模型说一句“完成了”就算完成。

## 1. 先用一句话理解

**业务 harness 是围绕模型组织执行的系统层：为它提供业务上下文和可用操作，管理执行状态、检查结果，并决定何时继续、停止或交给人。**

这里的 harness 是项目讨论采用的架构概念，不是一个统一的产品名。它可以实现为后端中的一组模块，不一定是独立服务，也不要求自主 Agent 或复杂框架。

如果只接收一段文本、调用模型、返回文字，主要解决的是“获得回答”。当系统要查询订单、创建任务、等待结果或修改业务记录，就需要进一步回答“是否允许、如何执行、如何知道成功、失败后怎么办”。这些是业务执行层需要补齐的部分。

## 2. 与普通后端是什么关系？

很多组成仍是熟悉的后端工程：接口、数据库、权限、状态、任务队列、日志、错误处理与测试。新增的难点是引入了模型判断：它可能理解错、选错操作、漏参数，或输出不符合契约的内容。

后端本来就要处理外部服务的不确定性；模型额外带来的是**内容看似合理但业务含义错误**的风险。JSON 合法，只能说明结构可读，不能说明订单、目标地点或操作选择正确。

| 后端职责 | 围绕模型时要多问什么？ |
|---|---|
| 请求输入 | 模型看到了哪些事实？缺失信息是否需要澄清？ |
| 业务函数／API | 模型能提出哪些操作？参数和权限由谁检查？ |
| 状态管理 | 当前步骤是否已经完成？后续操作是否有满足的前提？ |
| 错误处理 | 没收到回复与已执行但确认丢失，是否需要不同策略？ |
| 输出校验 | 格式正确之外，业务规则是否仍成立？ |
| 监控与测试 | 能否追查模型判断、实际操作和最终结果之间的差异？ |

因此：**后端可以承载 harness；后端不全是 harness；使用模型的系统也不必全部交给模型决定流程。**

## 3. 模型、业务知识、工具和 harness 分别做什么？

| 部分 | 负责什么 | 运输任务示例（设计示意） |
|---|---|---|
| 模型 | 理解表达、提取信息、提出处理建议 | 理解“送完这批货再去充电” |
| 业务知识 | 内部术语、流程说明与判断依据 | A 是哪个站点，哪些货物有特殊运输要求 |
| 实时业务数据 | 当前可核实的系统事实 | 订单状态、车辆位置、电量、充电位占用 |
| 工具／API | 查询或执行一项明确操作 | 查订单、创建运输任务、查任务状态 |
| 代码规则与权限 | 约束操作是否允许 | 校验用户权限、任务前提、参数范围 |
| 运行 harness | 组织上下文、状态、工具调用与反馈 | 等待运输完成，再检查充电条件；失败时停止或升级处理 |
| 评测体系 | 检查行为是否符合约定 | 是否漏步骤、越权、重复创建，或谎报完成 |

通用模型可能理解业务描述，但不会天然知道某企业的私有数据、内部代号和当前状态。应提供可查证的上下文与接口，而不是让它凭常识补全。“模型需要企业知识”也不等于必须重新训练模型；先明确缺的是文档、实时数据、规则还是操作能力。

## 4. 为什么不是一个意图配一个工具？

意图表达目标，工具表达可调用操作，二者通常是多对多。

- 一个运输意图可能要查订单、查车辆、创建任务和查完成状态。
- 查车辆状态的工具，也可以用于运输、充电与维修任务。
- 查制度、整理报告等任务未必需要业务写入工具。
- 工具可以是普通后端函数或已有服务接口，不一定要使用 MCP。

设计工具时先定义输入、输出、错误语义与副作用。例如 `create_transport_task` 返回任务 ID，只能证明创建成功，不能证明货已送达。`get_task_status` 返回权威系统的完成状态，才可能成为后续步骤的依据。接口名称本身不是成功证据。

## 5. “先送到 A，再充电”怎样从理解变成执行？

下面是未来业务设计示意，当前项目没有这些工具与运输状态机。“状态机”就是规定任务有哪些阶段、每个阶段允许转到哪里：例如“任务已创建→运输中→已送达”，不能把“已创建”直接当作“已送达”。

```text
用户表达目标
  ↓
模型提取任务、对象、地点和先后关系
  ↓
代码验证信息完整性、权限与执行前提；不清楚则澄清
  ↓
创建运输任务，保存任务 ID
  ↓
根据业务事件或状态查询等待结果
  ├─ 明确完成 → 重新查询电量、车辆与充电位状态 → 决定能否安排充电
  ├─ 明确失败 → 记录原因，按预定策略结束或转人工
  └─ 状态未知 → 核对既有任务，不能直接假定失败并重复创建
```

几个关键区别：

1. **识别出两个意图不等于执行两个任务。** 模型可以提出步骤，执行还要检查依赖和权限。
2. **“先后”不等于连续发两个 API。** 后一个步骤应等待前一个的约定完成条件。
3. **计划不能高于运行约束。** “先送货”若与必须停止的条件冲突，应按业务规则处理，不能只照语言顺序执行。
4. **创建不等于完成。** 必须记录任务引用，核实工具与业务系统结果。
5. **长任务不必让模型一直等。** 可以由后端工作流保存状态、消费事件，在需要判断时才调用模型。

## 6. 运行 harness 与评测 harness 是两套职责

| | 运行侧 | 评测侧 |
|---|---|---|
| 问题 | 一次业务请求如何处理？ | 这种处理方式是否符合要求？ |
| 输入 | 用户请求、遥测、当前业务状态 | 冻结样本、参考答案、故障用例 |
| 核心动作 | 校验、调用模型、合成决定、检查输出 | 按相同协议调用、计分、比较与留存证据 |
| 产出 | 业务响应、操作记录与执行状态 | 准确率、动作指标、失败与复现报告 |
| 本项目位置 | `embodied_brain/extended.py` 与 `router_v2/` | `eval/baseline_b/`、`eval/formal/` 等 |

两边应共享或验证相同的契约与规则，否则评测通过的东西可能不是实际部署的东西。但评测代码检查了预算，不代表业务 HTTP 入口也已经有同样的预算；Router 分类满分，也不能证明业务任务已经可靠完成。

## 7. 当前后端已经有哪些相关能力？

| 当前实现 | harness 视角的含义 | 证据与边界 |
|---|---|---|
| 输入检查与扩展租户选择 | 确定请求契约与处理路径 | [brain.py](../../src/cloud-orchestrator/embodied_brain/brain.py#L174)、[extended.py](../../src/cloud-orchestrator/embodied_brain/extended.py#L75)；租户选择不等于企业身份鉴权与数据隔离 |
| 三角色顺序调用、提前返回 | 固定工作流编排 | [extended.py](../../src/cloud-orchestrator/embodied_brain/extended.py#L119)；没有自主工具选择循环 |
| Router 严格 JSON 与结束原因检查 | 把不可用模型输出识别出来 | [pipeline.py](../../src/cloud-orchestrator/router_v2/pipeline.py#L122)、[prompt.py](../../src/cloud-orchestrator/router_v2/prompt.py#L73)；Safety／Compiler 的契约不同 |
| 代码计算风险、合成动作 | 不让模型删除已知数值风险 | [rules.py](../../src/cloud-orchestrator/router_v2/rules.py#L181)；备注独有风险仍可能漏判 |
| Compiler 后最终检查 | 模型输出不是最终执行授权 | [validate_actions()](../../src/cloud-orchestrator/router_v2/pipeline.py#L82)；只检查已定义的动作约束，不验证路径与目的地 |
| 返回 trace、决策与阶段耗时 | 可以观察处理过程 | [extended.py](../../src/cloud-orchestrator/embodied_brain/extended.py#L48)；不等于完整的持久审计平台 |
| Cosmos 状态读写 | 业务状态集成的一部分 | 当前尽力读写仿真状态；不等于持久化多步骤任务、恢复与事务实现 |
| 独立评测、封存和结果核对 | 检验模型处理与规则合成 | [report.md](../report.md)；正式测量主要是 Router／决策函数，HTTP 完整链路只用假依赖验证 |

所以面试可以说：**“后端实现了固定流程的模型执行编排，具备输入契约、角色衔接、结果校验和执行约束等 harness 能力。”** 不说已经建成通用企业 Agent 平台。

## 8. 当前没有做什么？

- 自由文本任务规划，以及运输、充电、维修业务工具的实际执行。
- 保存并恢复多步骤任务（持久化与异步恢复）、避免重复操作（幂等写入）、失败后作业务补救（补偿机制）。例如服务重启后找到未完成运输单；相同请求号重发不多建一单；运输取消后按规则释放已预留的充电位。当前均未实现。
- 企业身份认证、按用户／角色授权、工具级写入审批与完整审计体系。
- 模型根据环境反馈自主选择下一工具并循环执行。
- 上述业务能力在企业真实流程中的成功率与端到端延迟验证。

这些是拓展方向，不是当前必须补完的面试材料。对运行侧与评测侧分别核实，不能把一边的能力写到另一边。

## 9. 如果进入企业，从哪里开始设计？

以下是需求澄清顺序，不是技术选型承诺。

1. **选一个小任务**：明确谁提出请求、输入是什么、业务上怎样才算完成。
2. **列事实来源**：哪些来自文档，哪些必须查询实时系统，哪些需要用户澄清。
3. **选执行边界**：哪些只读，哪些写入，谁允许，哪些条件由代码强制检查。
4. **画状态与失败路径**：区分未开始、处理中、明确完成、明确失败、状态未知；规定恢复和重复请求如何处理。
5. **接最少工具**：先接可验证的小范围接口；固定流程可以由普通后端控制，不强求模型自主规划。
6. **先定验收再运行**：不仅看意图分类，还看参数正确性、约束遵守、任务完成、重复操作、错误处理、耗时和成本。
7. **用结果决定是否拆 Agent**：确有职责、权限或上下文隔离需求再拆，而不是按意图数量拆。

## 10. 面试追问怎么答？

### 这不就是普通后端换了一个名字？

后端是承载方式，harness 指围绕模型的执行职责。很多能力沿用后端工程，但需要额外把模型的语义错误、输出契约、上下文和操作边界纳入控制。只是把 API 换成 LLM、原样返回文字，还不能证明这些能力具备了。

### 提示词写上企业制度不就行了吗？

提示词可以告知规则，但不能代替实时数据、权限和执行检查。模型写“允许操作”不代表权限服务已放行；输出“已送达”也不能覆盖任务系统仍在运输的状态。读取到的业务内容也不能自动成为修改系统权限的指令。

### 需要照着 Codex 做一套吗？

可以借鉴“上下文→模型→工具→结果→继续或结束”的组织方式，但不必给业务 Agent 任意终端能力，也不必复刻编程助手界面。企业应用提供业务知识、数据、接口和权限；执行层管理模型与工具的交互。固定任务也可用普通工作流完成，不要求采购或采用某个具体产品。

类比依据：[OpenAI 官方文档 Codex as a platform](https://developers.openai.com/blog/codex-as-a-platform) 将应用拥有的业务上下文、规则和工具，与 harness 提供的执行循环等能力区分开来。此处借用职责划分解释概念，不把 Codex 的能力算成本项目的能力。（核对日期：2026-11-08。）

### 工具超时就重试，为什么还要设计失败状态？

读取失败和写入结果未知不同。创建任务的请求超时，可能是服务端已创建、回复丢失；盲目重发会重复创建。需要用同一请求标识核对已有任务，避免重复操作，这类设计叫幂等。当前评测预先规定“不重试、计错”，只是本轮测量政策，不是所有企业任务都不重试的通用结论。

### 多意图能做，为什么还需要工作流？

多意图识别解决目标提取，工作流解决先后、依赖、事实确认与失败。一个模型可以承担多种识别任务，但不能因此省略执行约束；也不需要为每个意图都配一个 Agent。

### 你项目的 300/300 能说明 harness 很可靠吗？

只能说明固定条件下 Router 对这批合成数据的表现，代码决策和压力验证另有范围。企业 harness 还要检验真实工具执行、权限、业务完成与恢复。本项目没有这些企业流程证据。

## 11. 30 秒口述

> 我把业务 harness 理解为后端中围绕模型组织执行的那一层。模型负责理解和提出判断，系统提供业务上下文与接口，并用代码控制权限、状态和结果检查。我的项目已经有输入契约、固定角色编排、严格解析、风险合成和最终动作校验，但还没有多步骤业务任务与工具执行循环。因此它体现了部分 harness 能力，不能说成通用企业平台。后续最重要的是把目标识别接到可核实的业务结果上，而不是继续增加 Agent 数量。

练习：不用术语解释“创建运输任务成功，为什么还不能去充电？”再指出当前项目哪几段代码分别对应输入契约、执行编排和最终校验。能回答这两题，再展开企业设计。
