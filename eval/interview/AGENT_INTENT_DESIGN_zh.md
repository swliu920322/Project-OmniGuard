# Agent、意图与路由：概念、当前实现和设计追问

用途：回答“一个 Agent 能处理几个意图”“为什么三个 Agent”“这算自主智能体吗”。本页区分概念、代码事实和未来设计，不新增实现或实验。示意输入不来自私有测试集。

字段看不懂时先读 [从这里开始](START_HERE_zh.md)。本页的 `primary` 就是“主要状态”，`risk_set` 是“全部风险清单”，`action` 是“当前动作决定”；不要把它们当作需要先学会的英文术语。

从识别进一步走到工具执行、状态管理和企业业务结果，配套读 [业务 harness](BUSINESS_HARNESS_zh.md)。

先记一句话：**意图或状态描述输入的含义，Agent 角色描述处理职责；类别数、角色数、模型数和调用次数是不同的数量。**

## 1. 从这些概念开始

| 概念 | 大白话 | 在当前项目里是什么 |
|---|---|---|
| 模型 | 执行语言处理与生成的底层能力 | 配置的模型 API；同一模型可以被不同角色反复调用 |
| 提示词 | 本次调用的规则与任务说明 | Router 的 B-1.0；Safety、Compiler 的各自说明 |
| Agent 角色 | 系统中承担某种职责的处理角色；称呼的严格程度需说明 | Router 分类，Safety 审查，Compiler 生成动作；当前是代码编排的模型处理步骤 |
| 意图 | 用户希望系统完成什么 | “安排运输，再查电量”是意图示例；当前遥测本身不表达用户请求 |
| 状态／风险 | 当前输入报告了什么情况 | 低电量、过热、障碍等；六类更准确地叫状态路由 |
| 路由 | 决定后续走哪条处理路径 | 当前按状态决定停车或继续后续阶段，没有六个对应的业务 Agent |
| 动作 | 系统最终允许做什么 | 返回 stop／move／turn 等结构；不是状态标签，也不等于真实执行 |
| 工作流 | 程序如何连接、选择和结束这些步骤 | HTTP 扩展路径的输入检查、模型调用、提前返回与动作校验 |

注意：角色通常围绕职责设计，但职责不是唯一划分维度。工具与权限、所需上下文、维护边界等也可以影响拆分；不能简单定义成“一个功能必须一个 Agent”。

## 2. “支持多类”和“单条多意图”不是一回事

### 一个 Agent 支持多类

不同输入分别可以属于正常、低电量、过热等不同类别。**一个 Router 可以支持全部六类**；只需明确输入、定义与输出契约，不需要训练六个模型或写六个 Agent。

### 一条输入包含多个意图

例如“先把货送到 A，再去充电”包含多个请求，还带顺序约束。一个 Agent 可以被设计来识别多个意图，但“可以设计”不等于当前已经实现或评测；不能靠增加提示词一句话就宣称可靠支持。

如果做这类任务，需要额外定义任务列表、对象参数、顺序、冲突、依赖、完成条件及失败策略，并用多意图样本验证。当前项目没有提供自由文本任务规划能力。

### 一条遥测包含多个风险

低电量、过热与障碍可能同时出现。这是**多风险状态**，不应直接叫多用户意图。模型只给一个“主要状态”（字段名 `primary`）；程序另外列出全部风险，合并模型报告的风险后，一次性决定动作。

**例子**：同时有障碍、过热和低电量，主要状态选障碍，全部风险仍有三项。当前决定是停车，保留冷却要求，回充留作待办。不是障碍处理完再处理过热、最后自动启动充电任务；当前没有这个任务执行过程。

六类主标签与六种备注状态也不是一回事：前者回答“走哪类处置”，后者回答“这句报告是当前肯定、否定、历史、假设、不确定还是无关”。两者一次调用共同输出，分别计分。

## 3. 两种常见结构：分发与串联

### 结构 A：按任务分发（教学设计，当前没有这些执行 Agent）

```text
输入 → 识别与分发
          ├─ 运输处理
          ├─ 回充处理
          └─ 维修处理
```

这里分类后选择不同处理者。下游既可以是模型 Agent，也可以是普通代码、服务或人工流程。多个类别也可以映射到同一个处理者，类别与 Agent 没有固定一对一关系。

若输入同时含多个任务，不能只把多个处理者一起启动：需要定义先后顺序、共享资源与冲突。运输与回充可能争用同一辆车，遇到必须停车的风险时也不能同时继续运输。

### 结构 B：按阶段串联（当前项目）

```text
输入 → Router 判断状态
           ↓
       代码合成风险与动作下限 ── HALT → 返回停车
           ↓ 可以继续
       Safety 审查规则 ─────── BLOCK → 返回停车
           ↓ 未拦截
       Compiler 生成动作
           ↓
       代码检查动作契约 → 放行或返回停车
```

主标签影响后续输入和约束；没有为六类分别调用六个业务 Agent。低电量和超速都可以走同一套 Safety／Compiler。源码见 [extended.py](../../src/cloud-orchestrator/embodied_brain/extended.py#L119)。

当前角色的连接由 Python 固定，模型不自行决定再找谁讨论，也没有根据反馈自主反复规划。不要把“按标签处置”和“动态委派给专用 Agent”混写。

## 4. 当前代码到底做到了什么？

| 问题 | 代码事实与定位 |
|---|---|
| Router 输出是什么？ | [prompt.py](../../src/cloud-orchestrator/router_v2/prompt.py#L49) 规定 `{"primary": ..., "note_status": ...}`，两格分别是“主要状态”和“备注判断”，不是多个意图列表 |
| 谁选择主标签？ | 模型预测 `primary`；参考标签由规范生成；执行主类由代码重新合成。三者不要混淆 |
| 数值的全部风险在哪？ | [rules.py 的 risk_set()](../../src/cloud-orchestrator/router_v2/rules.py#L73) 从数字计算，与模型单个标签无关 |
| 主标签怎么选？ | `PRIORITY` 的顺序：障碍、过热、低健康、低电量、超速；没有风险为正常。这是实验约定 |
| 多风险动作怎么定？ | [execute()](../../src/cloud-orchestrator/router_v2/rules.py#L181) 合并风险，[resolve_action()](../../src/cloud-orchestrator/router_v2/rules.py#L110) 一次合成；停车条件优先，冷却／锁定与后续待办保留 |
| 真正请求模型在哪？ | [pipeline.py](../../src/cloud-orchestrator/router_v2/pipeline.py#L37) 的适配器调用 `chat.completions.create`；`decide()` 把提示词与输入交给它 |
| 多个角色怎么传信息？ | [extended.py](../../src/cloud-orchestrator/embodied_brain/extended.py#L131) 中代码把主标签、遥测、规则等拼进后续调用；不是共享一个自主对话循环 |
| 每次一定调用三次吗？ | 不一定。急停／非法输入可不调用模型，Router 停车跳过后两段，Safety 拦截则不调用 Compiler；后两段还可能走 `ask_agent` 缓存 |
| 正式成绩测了三 Agent 优势吗？ | 没有。正式主测试测 Router，压力测决策函数；HTTP 全流程用假依赖测试，见 [正式报告](../report.md) |

## 5. 用一个例子讲明白

教学输入：距离 20 cm、温度 65℃、电量 15%，其他值正常，无备注。

1. 三个数值分别触发障碍、过热、低电量，代码风险集保留三项。
2. 按实验优先级，正确的模型主标签是障碍。模型不用输出三份意图或启动三个 Agent。
3. 代码最终动作是 HALT，保留 COOL，回充记为待办，不能一边停车一边立即移动去充电。
4. 扩展 HTTP 流程在 Router 决策后直接返回，Safety 与 Compiler 跳过。
5. 若模型误报 NORMAL_NAV，主标签准确率仍算错，代码会补回数值风险并停车；动作有兜底，不代表模型答对。

对照例子：遥测正常，备注写“前方可能有人”。模型应给 `UNCERTAIN`，使代码加入障碍风险。如果模型的备注状态和主标签都漏掉这个风险，数值代码无法从正常遥测里凭空补出“有人”，可能漏停。

## 6. “这其实只是工作流，为什么叫 Agent？”

这是合理追问，不需要争名称。

> 项目沿用 Router、Safety、Compiler 的 Agent 角色命名。严格说，当前实现是代码控制的多角色 LLM 工作流：顺序和提前退出由程序规定，没有自主规划与工具反馈循环。我不会把它描述为三个自主智能体协商。

命名没有跨场景唯一口径。作为参考，Anthropic 在 [Building effective agents](https://www.anthropic.com/research/building-effective-agents) 中区分预定代码路径的 workflow 与模型动态控制过程及工具使用的 agent，也区分串行链和按类别分发。这里采用该区分解释本项目，不把它当作所有系统的唯一标准。（核对日期：2026-11-08。）

本项目对 Cosmos 的读写由代码发起，Compiler 输出的动作数组也不等于模型使用工具调用协议自主执行了设备操作。

## 7. 一个 Agent 还是多个，怎么作设计判断？

先确定业务需求，再选最简单且可验证的实现。以下是设计分析，不是本项目已完成的性能比较。

| 方案 | 可能适用的情况 | 需要付出的代价／验证 |
|---|---|---|
| 普通规则与代码 | 有明确数值阈值、枚举与动作限制 | 验证边界、缺失值和组合；不必为此增加模型调用 |
| 一次结构化模型调用 | 多类输入能共享上下文与输出契约 | 验证类间混淆、备注语义、格式和失败；单次模型也可能有长尾延迟 |
| 按任务分发 | 下游工具、权限、知识或处理过程确实不同 | 验证选错处理者、上下文交接和任务冲突；下游不一定要是 Agent |
| 多阶段串联 | 有明确的步骤依赖，希望逐段观察或维护 | 增加调用与交接，可能传播上游错误；需要与简化方案对照 |
| 模型自主循环 | 任务步骤难预先规定，需要根据环境反馈选择下一步 | 需要迭代、费用与时间限制，以及工具结果验证；当前未实现 |

一个 Agent 可以支持多种意图，但是否处理得好，要看评测；多个 Agent 也不是天然更专业或更可靠。是否拆开，应有可说明的职责或权限边界，以及可检验的收益。

## 8. 追问到取舍时，怎么回答？

### 为什么拆成三个，不能一次输出状态和动作吗？

可以设计一次输出。当前拆分便于分别显示和记录分类、规则审查与动作生成，但没有做单段与三段的同任务对照（也叫消融比较，即去掉或替换某段看效果），不能声称三段更准确或更快。无论几次模型调用，最终动作仍应由确定性代码检查。

### 研究延迟，串行调用是不是与目标矛盾？

它带来需要被测量的开销，这是设计取舍，也是研究对象。当前记录能展示特定链路的调用耗时；未证明该架构是低延迟方案，也没有量化真实车辆的允许等待时限。下一轮才适合比较简化链路与保留链路。

### Safety 是第二个模型，会不会纠正 Router 的所有错误？

不能这样保证。当前 Router 合成 HALT 时直接结束；继续时，Safety 收到主标签、数值与规则等，没有独立重做备注识别的完整契约。它也可能犯错，同一模型的不同角色并非相互独立的专家。可检查的数值与动作限制由代码执行，模型审查不能替代这些限制。

### 六类为什么不做六个 Agent？

类别本身没有证明需要六套处理者。当前数值类别可用规则判定，多个类别共享审查和动作格式。只有下游职责、工具、权限或上下文差异值得隔离时，才有理由考虑拆分；不能用标签数决定 Agent 数。

### 如果真要做一句话多意图，现有协议够吗？

不够。`primary` 只有一个标签，备注也只有一个受限话题。真正任务多意图需要新协议，例如任务列表与依赖，但那是新业务范围，不能把当前多风险测试当作它的证据。

### 为什么不把三段并行，降低延迟？

当前后段输入依赖前段结果，直接并行会改变任务语义。可以设计独立检查并聚合，但必须重新定义数据传递、冲突与停止规则再比较。不存在“把顺序调用改成并发就等价”的结论。

### 真要验证拆分值得，实验怎么做？

预先固定同一任务、金标、计分和可比的模型设置，对比规则、单次结构化调用、三段调用；最终动作代码约束保持一致。每种分别报告模型预测与动作效果、请求失败、延迟分布、调用数和费用。串行延迟按每条完整记录计算，不把各段中位数相加冒充总中位数。若依据错误调参，留在开发资料，最终用未接触测试验证。这是后续方案，当前没有执行。

## 9. 30 秒口述与自查

> 我把输入类别和处理角色分开看。一个 Router 支持六类状态，并不需要六个 Agent；当前三个角色按判断、审查、动作生成分工，由代码串联。多风险时模型输出一个主标签，代码保留完整风险并合成动作。严格说它是多角色 LLM 工作流，不是自主多 Agent 协商。拆分便于观察，但有额外调用开销，我还没有证明它优于一次结构化调用。

不看稿回答六题：

1. 六种类别与三个角色各自数的是什么？
2. 一条输入同时低电量与过热，为什么不启动两个业务 Agent？
3. 一个模型调用输出两个字段，为什么不是两个 Agent？
4. 当前为什么更接近工作流？谁控制下一步？
5. 如果去掉 Safety，需要怎样比较才能知道影响？
6. 模型说正常但代码停车，分类准确率该怎么算？

能回答这些，再谈扩展设计。概念材料补齐不代表本人已完成口述验收。
