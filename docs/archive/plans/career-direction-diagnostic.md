## 二、你是什么类型的工程师

从这段时间的对话来看，你有几个非常鲜明的特征：

### 你擅长的

1. **跨领域模式识别** — 你能在机器人安全和文档渲染之间发现"确定性回退"的同构结构。这不是大多数工程师具备的能力。
2. **系统思维** — 你思考的不是"怎么写这个功能"，而是"这个系统的信任边界在哪、成本结构是什么、哪些是契约哪些是实现"。
3. **自我怀疑的能力** — "这不就是呈现组件的不同么"——大多数人做完 demo 就沾沾自喜了，你会回头质问自己。这是高级工程师的标志。
4. **写作能力** — 你的哲学文档和 LinkedIn 帖子的质量远超一般工程师的文字输出。

### 你不擅长的（或者说你的倾向性弱点）

1. **收敛** — 你容易被新想法吸引，在当前项目做到 60% 时跳到下一个。AI 命理、人生进化器、Content Interpreter——每一个都是你在某个时刻被某个洞察激发后开始的，但你很难把一个东西推到"完成"。
2. **区分"有趣"和"有用"** — AI 六爻很有趣，但它对你的求职没有帮助，对你的技术成长也没有帮助。你花在上面的每一小时都是从 OmniGuard/Content Interpreter 上偷来的。
3. **面试叙事** — 你有很多好素材，但你还没有把它们组织成一个连贯的"这是我，这是我能做什么"的故事。

### 你真正想做的

你自己说了："我其实感觉我想做产品或者是应用落地。"

这和你的行为模式一致——你做 AI 命理不是因为你想做算命，是因为你想做一个**用户可以摸到的东西**。人生进化器也是。Content Interpreter 也是。你的兴奋感来自于"一个人打开这个页面，和它交互，被它打动"——而不是来自于"这个 Azure Function 的冷启动时间优化了 200ms"。

**你的方向是：AI 产品工程师 / AI 应用架构师。** 不是纯云架构（太枯燥），不是纯前端（太浅），不是纯 AI 研究（不是你的强项）。你的独特定位是：**在 AI 能力和用户体验之间设计信任边界。**

这正是 Content Interpreter 做的事情——AI 决定什么、代码保证什么、用户感知什么。这个三角形就是你的核心能力叙事。

## 三、你应该做到什么程度

### 不需要做到产品级。需要做到"故事级"。

面试不是产品评审。面试官不会去 `npm install @omnidocs/interpreter` 然后跑你的测试。面试官需要的是：

1. **一个可以 30 秒演示的东西**（屏录/链接）
2. **一个可以 5 分钟讲清楚的架构故事**
3. **2-3 个可以深入追问的技术决策点**

你的 Content Interpreter v3 已经满足了这三个条件：

| 条件 | 当前状态 |
|:---|:---|
| 30 秒演示 | ✅ 切换三种形态 + 输入意图 + 看结果变化 |
| 5 分钟架构故事 | ✅ 五层编译管线 + 信任边界 + 确定性回退 |
| 深入追问点 | ✅ grammar-constrained GPU / sanitize 消毒 / 规则优先于模型 |

**你现在不需要再加功能。你需要练讲。**

### OmniGuard 也一样

OmniGuard 有两个可以深入讲的故事：

1. **学术故事**：Kinematic-Token Theorem — "我证明了云端 LLM 控制的物理安全约束，推导出最大安全速度公式"
2. **工程故事**：多 Agent 编排 on Azure — "Router → Safety → Compiler 三级 Agent，延迟预算分配，ACA + Functions 的选型取舍"

每个都够讲 10 分钟。你不需要把 OmniGuard 做得更完善，你需要把这两个故事**练到可以白板画出来的程度**。

## 四、面试叙事设计

### 你的一句话定位

> "我是一个做 AI 应用架构的工程师。我的核心能力是设计 AI 和确定性代码之间的信任边界——让 AI 做决策，让代码做保证，让系统在模型出错时不崩溃。"

这句话覆盖了你所有的好项目：
- OmniGuard 的 edge fallback = AI 出错时本地模型兜底
- Content Interpreter 的 sanitize + 规则引擎 = AI 出错时确定性回退
- 两个领域同一个模式 = 你不是碰巧做了两个项目，你有一个可迁移的架构认知

### 面试时的三段式讲法

**开场（1 分钟）：定位**
> "我做的核心事情是设计 AI 和应用代码之间的边界。我在两个不同领域验证了同一个架构模式——一个是机器人安全，一个是文档智能渲染。"

**主体（5-8 分钟）：选一个项目深入讲**

取决于面试职位：
- 如果是**云架构/后端**方向 → 讲 OmniGuard（Azure 多 Agent 编排 + 延迟预算 + 边缘回退）
- 如果是**前端/全栈/AI 应用**方向 → 讲 Content Interpreter（FormSpec 参数化引擎 + 消毒层 + grammar-constrained GPU）
- 如果是**AI 工程**方向 → 两个都简要讲，重点讲跨领域同构（"确定性回退"作为通用架构原语）

**收尾（1 分钟）：拉回来**
> "这两个项目教会我的是：AI 应用的核心设计不是模型选型或 prompt engineering——是界定 AI 做什么决策、代码保证什么不变性。这是我想继续深入做的方向。"

### 面试时会被追问的 Top 5 问题（提前准备）

| 问题 | 你应该怎么答 |
|:---|:---|
| "为什么用 grammar-constrained 而不是 JSON mode？" | JSON mode 是语义级约束（模型可能输出合法 JSON 但值无效），grammar 是语法级约束（模型连无效值都打不出来）。语法 ⊂ 语义——更严格、更适合安全场景。 |
| "sanitize 层的具体策略？" | 白名单枚举校验（pick from allowed set），未知字段丢弃（防注入），缺失字段用 academic 默认值填充。trust.test.ts 里有 proto 污染测试。 |
| "为什么规则优先于模型？" | 0.5B 模型理解力有限，grammar 只锁住格式不锁住语义——它会"自信地选错"。实测发现它在所有不确定 case 里都选 academic（挑默认项）。所以：规则有把握时绝不咨询模型。 |
| "这和传统模板引擎/CMS 的区别？" | 直接用你 LinkedIn 帖子里的三个 axis：what changes / how many inputs / who chooses。 |
| "你觉得这个方向的局限是什么？" | 当前的"受限自由"路线牺牲了开放式生成的灵活性。如果用户想要完全自定义的 layout（不在预设参数空间内），系统无法满足。这是一个有意识的取舍——安全 vs 自由度。 |

## 五、关于 AI 命理 / 六爻 / 人生进化器

### 诚实的建议：在面试准备期间暂停它们

不是因为它们没价值——它们有。AI 六爻（英文版易经）是一个很有意思的 niche 产品方向。人生进化器的游戏化任务系统也是一个真实的产品需求。

但它们有两个致命问题：

1. **面试时不好讲。** "我做了一个 AI 算命应用"——面试官会在心里打一个问号。你需要花大量时间解释"这不是迷信，这是一种基于卦象的意图映射"，而这个解释本身就已经偏离了技术讨论。
2. **它们分散你的注意力。** 你现在最需要的是把 OmniGuard + Content Interpreter 的故事**练到滚瓜烂熟**。每一个小时花在六爻上的时间，都是从面试准备里偷走的。

**建议**：把六爻和人生进化器放进一个"Side Projects"文件夹，面试拿到 offer 后再继续。如果面试官主动问"你业余做什么"，可以轻描淡写提一句"我在探索 AI 在非传统领域的应用，比如用 LLM 做意图映射的咨询工具"——但不要主动展开。

## 六、LinkedIn 帖 #2 和 #3

帖 #1 的核心是"AI+app 的边界在哪"——面向广泛的技术受众。  
帖 #2 和 #3 应该服务于**你的求职叙事**。

### 帖 #2：工程深度帖（周三）

**标题方向**: *"A 0.5B model kept picking the default answer. Here's what that taught me about AI trust boundaries."*

**核心内容**：讲你在 `local-gpu.ts` 里发现 0.5B 模型"总是自信地选 academic"的故事。这是一个真实的工程教训，不是理论推演。然后展开你的解决方案：规则引擎先跑 → 有把握就不问模型 → 模型只在不确定时被咨询。

**为什么这篇有面试价值**：它展示了你在 AI 工程中的实战判断力——不是"模型越大越好"，而是"知道模型什么时候不可信，并设计工程手段来处理它"。这正是 AI 应用架构师最稀缺的能力。

**结构建议（800-1000 字）：**

1. Hook："We put a 0.5B model in the browser. Grammar-constrained. Physically can't output invalid JSON. Sounds safe? It wasn't."
2. 故事：模型在所有不确定 case 里都选 academic（挑默认值）。Grammar 锁住了格式，但锁不住语义。
3. 你的解决方案：三级策略（规则有把握 → 直接用 / 规则不确定 → 咨询模型 / 模型失败 → 规则兜底）
4. 提炼出的原则："Rules own certainty. Models own ambiguity. Code owns safety."
5. 和 OmniGuard edge fallback 的同构："Cloud too slow → local model. Model unreliable → rules. Same primitive."
6. CTA："What's your strategy when the model is confidently wrong?"

### 帖 #3：跨领域洞察帖（周五）

**标题方向**: *"I found the same architecture pattern in robot safety and document rendering. I don't think that's a coincidence."*

**核心内容**：把你最独特的能力——跨领域模式识别——做成一篇帖子。讲 Kinematic-Token Theorem 的 edge fallback 和 Content Interpreter 的确定性回退是同一个东西。

**为什么这篇有面试价值**：它让面试官看到你不是一个"给什么需求做什么功能"的执行者，而是一个能在不同领域之间发现底层结构的思考者。这种帖子在 LinkedIn 上非常稀缺，转发率通常很高。

**结构建议（600-800 字）：**

1. Hook："Two completely unrelated problems. One architectural primitive."
2. 领域 A：机器人安全——云 AI 太慢，车辆盲行，edge fallback 兜底
3. 领域 B：文档渲染——AI 输出不可信，确定性模板兜底
4. 同构点：都是"约束 AI 的决策空间，在 AI 失败时有确定性回退"
5. 提炼："Constrain the decision, not the output" 是一个通用的 AI 应用架构原语
6. 个人反思："I didn't plan this. I built two things, and only later realized they share the same skeleton."
7. CTA："Have you seen this pattern in your own work?"

## 八、一句话总结

你不缺想法，不缺品味，不缺技术能力。你缺的是**收敛**。

把所有精力集中在两个项目（OmniGuard + Content Interpreter）、三篇帖子、五个面试答案上。砍掉其他一切。

你的定位是"AI 应用架构师——设计 AI 和确定性代码之间的信任边界"。这个定位既覆盖了你的学术项目，又覆盖了你的工程项目，又覆盖了你最想做的"产品/应用落地"方向。

不要再开新项目了。把已有的两个讲透、发出去、面试拿 offer。

然后你想做 AI 六爻还是人生进化器，随你。
